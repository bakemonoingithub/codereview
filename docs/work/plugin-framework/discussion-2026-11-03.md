# 插件体系设计讨论纪要

日期：2026-11-03。状态：讨论结论，尚未进入实施。承接 [JSON 形式插件与统一插件执行器设计讨论](README.md)（2026-11-01）。

## 1. 背景与定位

- 系统部署在制造业内网，支持在线代码审查，无须把代码拉到本地。
- 客户端环境受限（Win7、依赖缺失），本地 coding agent 基本无法安装，算力集中在服务器。
- 面向管理者等非技术用户，提供了解项目的入口。
- 接入业务系统时，在线系统便于审计和赋权。

结论：将 Agent 能力以内网服务形式提供是合理分工；插件体系是在此基础上接入更多内网系统。

## 2. 总体原则

- 先用一个有实际价值的场景证明价值，再从真实插件中提炼框架，不先行定稿通用 schema。
- 降低「零代码导入」预期：标准 REST + JWT 系统可以通过 JSON 接入；老系统（SOAP、自定义签名、session 登录等）仍需可信适配器。
- 优先接入近五年建设、使用 JWT 鉴权的系统。
- JWT 过期由执行器内置「登录续期」认证适配器处理：服务账号换取 token、缓存，过期或 401 时自动重新获取，避免逐个改造业务系统。前提是各系统提供受限服务账号。
- MCP 出口排在最后，只保证内部接口清晰、可扩展。

## 3. 分层结构

| 层 | 职责 |
| --- | --- |
| 插件 | 能做什么：操作目录、参数、请求映射、响应处理 |
| Skill | 为某个业务目标如何做：输入表单、引用的工具、提示词、完成标准 |
| 任务入口 | 用户选择 skill、填写表单、发起任务 |
| 执行核心 | 多轮循环、工具调用、取消、预算、调用记录，所有入口共用 |

- 不在现有 Agent 分析入口中混入插件任务，避免填写虚假的仓库或 SHA、放松原有约束。
- 不按插件开设入口，按任务类型或 skill 组织。
- 可为少数技术用户保留「自由插件分析」入口，用于发现值得沉淀为 skill 的场景（待定）。

```mermaid
flowchart LR
    A[维护者编写 skill] --> B[保存时校验依赖]
    B --> C[用户选择 skill 并填写表单]
    C --> D[运行时校验连接与可用性]
    D --> E[填充提示词模板并锁定范围]
    E --> F[只将声明过的工具交给 LLM]
```

## 4. Skill 设计

### 4.1 作用

- 由管理员或熟悉技术、业务的人员维护，不直接把插件暴露给用户。
- 引导 LLM 按正确路径查询数据。
- 倒逼维护者检查插件工具集是否齐全、描述是否合理，减少 LLM 因工具与目标之间存在缺口而无法结束任务。
- Skill 只是引导，不授予权限；执行层白名单与范围锁定仍是最后一道关。

### 4.2 格式

- 编辑采用 YAML，校验采用 JSON Schema，存储转为 JSON；与插件 JSON 共用校验机制。
- 提示词写在 skill 文件内，一个 skill 是完整单元，便于导入导出和版本管理。

示意（字段名非定稿）：

```yaml
schemaVersion: skill/0.1
id: issue-code-impact
version: 1.0.0
name: 根据 Issue 评估代码改动点
inputs:
  - key: issueKey
    label: Issue 编号
    type: string
    required: true
  - key: repo
    from: system.code-repo
  - key: ref
    from: system.code-repo
tools:
  - plugin: jira-4
    operations: [getIssue]
    scope: { issueKey: "{{inputs.issueKey}}" }
  - plugin: system.code-repo
    operations: [tree, find_files, search_code, read_code]
prompt: |
  你需要根据 Issue {{inputs.issueKey}} 的描述，在 {{inputs.repo}}@{{system.resolvedSha}} 中……
completion:
  required: [改动点, 影响范围, 风险]
  onMissing: 列出缺失材料后结束
```

### 4.3 校验

- 保存时（静态）：格式与 schema 版本；引用的插件与操作是否存在、版本是否兼容；模板变量是否都已声明；`scope` 锁定的参数属于对应操作。
- 发起时（运行时）：连接是否可用（权限体系补齐后再加用户权限校验）。
- 运行时只暴露 skill 声明过的操作。

### 4.4 变量

| 类别 | 写法 | 来源 | 处理 |
| --- | --- | --- | --- |
| 表单变量 | `{{inputs.*}}` | 用户提交，经 schema 校验 | 任务开始前替换，可用于范围锁定 |
| 系统变量 | `{{system.*}}` | 服务端生成，如解析后的 SHA、时间、任务编号 | 任务开始前替换 |
| 流程中产生的值 | 不作为变量 | LLM 从工具结果中取得，属于材料 | 用自然语言描述流程，由 LLM 传参；必要时用参数 schema 约束 |

- 模板替换只在任务开始前执行一次，运行过程中不替换。
- 防止引用未声明变量，防止材料内容被当作指令或权限参数注入。

## 5. 发起表单

由 skill 声明的字段动态生成，另有公共部分：

| 字段 | 处理 |
| --- | --- |
| Skill | 必填 |
| 本次要求 | 必填，自然语言 |
| 任务名称 | 可选，默认自动生成 |
| 连接 | 第一批规定一个插件只绑定一个连接，表单不出现 |

第一批不做：补充材料（格式、编码、大小、OCR 均不确定）、模型与预算档位（内网仅 ds4.0flash）、可见范围（暂无权限体系）。

缺参处理：

- 动态表单与执行层范围锁定减少缺参。
- 插件提供列表、搜索类操作，参数校验失败时返回明确错误，LLM 自行查找修正。
- 仍缺关键信息时「结束并追问」：任务以「需要补充信息」结束，列出问题与已查到内容；用户补充后发起新任务，带上原输入和结论摘要。
- 不做暂停等待式多轮对话（涉及任务挂起恢复、状态机、审计和前端改造），按实际追问频率再评估。

## 6. 代码仓库系统插件

现有 Agent 工具（`AgentToolNames.java`，版本 `agent-tools-v1`）：`tree`、`find_files`、`search_code`、`read_code`、`read_diff`，均为只读；`submit_result` 属于执行核心，所有 skill 共用。

- 封装为内置「代码仓库」系统插件，可在 skill 中按操作引用。内网 Gitea 查代码不便，该插件是对其的能力扩展。
- 与 Gitea 插件分工：Gitea 插件经 API 查 PR、Issue、提交、分支；代码仓库插件基于本地镜像执行 git。
- 同样采用插件声明（操作目录、参数、指南），执行方式为内置实现，不可导出或修改。
- 声明任务输入：仓库（必填）、分支或提交（必填，运行时解析为固定 SHA）。现有代码分析表单迁移为该声明。
- 本地镜像从 Gitea 连接同步，两者按仓库关联。
- 代码证据保留 SHA、路径、行范围语义。

## 7. 首个接入：Jira Issue

选择理由：Jira 主版本为 4，接口文档可查，鉴权可处理；小需求在 Issue 中管理，按编号定位方便；场景明确。

| 场景 | 安排 |
| --- | --- |
| 3.1 根据 Issue 查代码改动点并评估 | 首个 skill；Jira 读操作 + 代码仓库插件，链路最短 |
| 3.2 结合历史 Issue 评估新需求 | 第二个 skill；先由用户手动填写相关单号，自动查找后续再做 |
| 3.3 JQL 统计 | 只读可做；统计本身直接调 JQL，LLM 负责解读；分页必须取全 |
| 3.3 评论 Issue | 首个写操作，推迟；需单独设计审计、内容确认、防重复提交 |

第一批范围：Jira 插件只读（搜索、取详情、JQL）+ 代码仓库系统插件，实现 3.1 一个 skill。

技术风险：Jira 4 的 REST 接口较早期，与现行 `/rest/api/2` 不完全一致，部分能力可能仅有 SOAP 或 XML-RPC。需以实例具体小版本核实搜索、取 Issue、JQL 能否通过 REST 调通，再决定纯 JSON 插件还是加适配器。

## 8. 结果展示

复用 Agent 分析的三个标签页：

1. 分析结果：纯 Markdown 渲染。
2. 任务属性：skill 名称与版本、使用的连接、表单值、完整性状态（完整、截断、查询失败）。
3. 工具调用记录。

证据链：

- LLM 引用具体某次调用的编号，并补充一两句说明依据的是结果中的哪一部分。
- 提交时执行层校验引用的调用存在于本任务且成功返回。
- 结果中的引用渲染为链接，点击跳到对应调用记录。
- 代码证据（SHA、路径、行范围）与插件证据（调用编号、取得时间、说明）并存，`submit_result` 结构需同时容纳。
- 说明只概括材料中已有内容，推断须明确标注。

## 9. 模型能力

- 内网 ds4.0flash 已能完成一次 Agent 分析，理论可行；必要时调整响应限制。
- 插件响应更杂（Issue 描述长、含格式标记和评论），优先在插件响应处理中裁剪字段，而非单纯放宽限制。
- 3.1 需从业务描述提炼代码关键词；效果不佳时在 skill 指南中给示例，或增加「涉及模块」可选表单字段。
- 建议用 5–10 个真实历史 Issue 实测 3.1，与开发者实际修改位置对比命中率。

## 10. 待定事项

- 权限体系：暂缓讨论。在此之前服务账号须配置为只读、最小范围；接入敏感业务系统前应补齐用户权限。
- Jira 4 实例的具体版本与可用接口核实。
- 插件与 skill 的正式 schema、操作身份格式、版本与更新机制。
- 「自由插件分析」入口是否保留。
- 证据存储与保留策略。
- 结论页面向非技术读者的呈现，在 HTML 原型阶段打磨。
