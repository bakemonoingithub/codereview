## 2. 现状与缺口

| 当前实现 | 缺口与影响 |
| --- | --- |
| `SpecialistResultView.vue` 展示三类结果，且被报告创建预览、报告来源阅读复用 | 直接改变公共默认布局会影响 tab 之外的页面 |
| `review_result.body` 保存不可变分析正文 | 模式候选和依赖解读目前只在 JSON 数组内，没有独立持久化 ID |
| `issue` 为问题审查提供稳定 ID | 不适合以虚构问题记录承载模式或耦合条目 |
| `feedback` 按 `(subject_kind, subject_id)` 唯一保存评价与评论 | 服务只接受 ISSUE、RESULT；每张卡复用 RESULT ID 会互相覆盖，自行拼 ID 会被拒绝 |
| `TaskStatisticsService` 分别统计问题和整份模式／耦合结果 | 缺少条目级数量、未反馈数与准确率；不能静默更换旧字段的统计单位 |
| `ReportInputService` 与 `ReportFactsBuilder` 冻结并使用问题反馈或整份结果反馈 | 新条目反馈需进入新报告快照，旧报告继续使用原冻结含义 |

依据已核对 `db/agent-migration/V1__agent_init.sql`、`AgentDatabase`、`SpecialistResultPublisher`、`FeedbackService`、任务 DTO 与上述统计、报告组件。本轮未连接真实数据库，表结构判断依据仓库迁移链，不宣称实际库已核验。

## 3. 前端范围与实现落点

### 3.1 结果 tab 专用展示

建议新增 `SpecialistReviewResultTab.vue`，只在 `TaskDetail.vue` 的 `activeTab === 'result'` 分支使用。沿用现有 `result`、`taskId`、`open-code` 传递方式，继续通过现有代码引用工具还原固定版本坐标。公共 `SpecialistResultView.vue` 在报告预览等位置保持现有默认行为。

新视图按原型组织：

| 区域 | 前端落实 |
| --- | --- |
| 总结 | 明确结论标题、摘要和当前文件的条目数量；问题审查补充高／中／低严重度数量，移除正文中的「协议 v1」 |
| 问题审查 | 卡头展示编号、中文严重度、类型及标题；正文分问题说明、变更关系、修改建议、问题位置与辅助证据 |
| 耦合度 | 程序解析事实与模型解读分区；保留依赖指标、版本侧、关系表、材料限制；每条解读展示说明、关联依赖、可选建议与代码依据 |
| 设计模式 | 每个候选展示中文分类、名称、目标角色、说明及代码依据；不增加协议没有的置信度或严重度 |
| 反馈 | 每张明细卡提供独立评价、直接展示的可选评论、清除评价、保存与状态；顶部总结和依赖事实不提供评价 |
| 空结果／未完成 | 保留结论边界；空结果无条目反馈；未完成只展示成功片段，不提供反馈或冒充完整结论 |

模式分类覆盖创建型、结构型、行为型与其他；未知枚举保留可识别的缺省显示。长正文、多个位置、跨文件证据、无建议、无辅助证据、空摘要、缺失材料都依据实际字段处理，不使用原型示例填补。

### 3.2 反馈组件与范围隔离

复用 `FeedbackEditor.vue` 的保存、草稿及冲突处理；新增仅供本 tab 启用的展示参数，以调整卡片底部布局与提示文案。其余调用方保留默认布局。评论始终显示，清除评价不清空评论，允许只保存评论，保存成功前不显示已保存。

前端依据服务端条目 ID 绑定反馈，不能用渲染数组下标、标题或临时 UUID 作为保存主体；服务端返回原始序号用于正文关联，前端排序不能改变反馈对象。保存后刷新当前条目的反馈及相应统计，保留未提交的新输入。

不调整任务头部、目标文件列表、输入与配置、实际调用、Agent、报告表单及报告阅读页面的布局。现有离页保护、异步隔离、错误重试和代码阅读继续有效。

## 4. 数据库方案：新增一张索引表

以下为待后端授权后实施的技术方案。本轮不创建迁移脚本或执行 SQL。

拟新增 `review_result_item`，仅保存条目身份及归属，不复制分析正文：

| 字段 | 建议类型 | 含义 |
| --- | --- | --- |
| `id` | `CHAR(26)` | 服务端分配的稳定条目 ID |
| `result_id` | `CHAR(26)` | 所属 `review_result.id` |
| `kind` | `VARCHAR(20)` | PATTERN 或 COUPLING |
| `ordinal` | `INT` | 已发布正文中的原始序号，从 1 开始 |
| `created_at` | `DATETIME(3)` | 索引建立时间 |

主键为 `id`，增加 `(result_id, kind, ordinal)` 唯一索引，支持按结果定位与重复执行防重。最终 DDL 在 SRF-02 核对当前迁移链后定稿；只追加新迁移，不修改已经执行的旧迁移文件。

现有 `review_result`、`issue`、`feedback`、`report_source` 不增删字段。`feedback.subject_kind` 当前为 `VARCHAR(10)`，可容纳 PATTERN、COUPLING；`subject_id` 继续保存 26 位 ID，现有唯一索引与 `revision` 条件更新可复用。注册新实体及 Mapper 时沿用现有独立 Agent 数据源，不接入外层历史库。

结果先完成既有合并、校验和去重，再为完整的模式／耦合结果按最终正文数组建立索引；结果、条目与任务终态按既有发布事务保持一致，避免结果可见但条目未建立。问题审查继续使用 `issue`；空数组产生零条索引；未完成结果不提供可反馈条目，Agent 不创建本次索引。

## 5. 历史回填与全新部署

### 5.1 已有试运行数据

在获得实际数据库操作授权后，为已有 COMPLETE 的 PATTERN／COUPLING 结果补建索引。回填读取保存的正文与原始顺序，不重新调用模型，不重新合并条目，不修改原正文、问题记录、原反馈或冻结报告。

建议在应用对外接收任务和反馈之前，以可重复执行的受控启动步骤完成回填：分批扫描、每份结果单独事务、按唯一索引防重，已建立的条目 ID 不重新分配；必须核对已有索引的类型、序号与条目数，不能只判断“存在任意一条”就跳过。多实例竞争时读取已经成功建立的 ID。中断后重试补齐剩余数据。

遇到不可解析正文、类型不一致或索引缺口应明确失败并定位结果，不将失败记录当作零条目继续提供可写服务。记录扫描、补建、已完成和失败数量；不输出模型凭据或完整敏感正文。实现时验证此步骤与调度启动的顺序。

历史 `subject_kind=RESULT` 反馈保留为历史数据，不自动分配给每条结论，不计入新的条目准确率。当前结果 tab 不增加整份结果评价入口；历史冻结报告继续读原有快照。回退采用备份恢复与匹配版本部署，不能仅回退前端、保留不兼容接口；不自动删除新表或新反馈。

### 5.2 内网从零部署

沿用现有 `AgentDatabase` 的身份检查与 Flyway 初始化链，执行追加迁移创建新表。空库的历史回填扫描为零；新分析发布时自动生成条目 ID，用户直接逐条反馈，不需要手工迁移、创建索引或再次发起分析。

隔离空库初始化、已有数据升级、重复启动三种路径分别验证。编写迁移脚本不等于已验证内网部署；实际内网部署不包含在本轮文档授权中。

## 6. 接口、统计与报告衔接

### 6.1 读取与保存

保留现有结果正文和 `issues` 含义，建议在结果 DTO 追加 `items`，每项包含 `id`、`kind`、`ordinal`，与已保存的 patterns／observations 对应；不要求模型生成 ID，不改变模型输出 JSON 协议。完整结果索引缺失时返回明确错误，不给前端虚假可保存状态。

继续使用 `GET/PUT /api/v2/feedback/{subjectKind}/{subjectId}`，新增 PATTERN、COUPLING 主体；保存正文仍为 `assessment`、`comment`、`expectedRevision`。服务端校验条目存在、类型一致、所属结果完整，并复用版本冲突与竞争保护。ISSUE 原能力继续有效，既有 RESULT 接口行为保留以免破坏原消费者；当前新 tab 不发起 RESULT 保存，不为历史整份反馈新增编辑入口。

### 6.2 统计口径与 tab 外边界

新增按 PATTERN／COUPLING 条目 ID 聚合的统计，包含完整条目总数、准确、不准确、无法判断、未反馈及无分母状态。使用索引表查询全部对象，不因尚无反馈行而漏算分母，不在每次统计时解析全部分析正文。三类分别统计，旧 RESULT 反馈不折算为条目反馈。

现有 `/statistics` 的 `issues`、`results` 单位保持原义；条目统计使用明确新增字段或独立接口，不把条目数量塞进 `results` 冒充整份结果数量。接口字段在 SRF-02 定稿。

任务顶部 `TaskAccuracySummary.vue` 位于授权 tab 之外，当前读取整份模式／耦合结果统计。仅改变后端字段含义会使顶部说明失真，原样保留则不会反映新条目反馈。因此将“顶部保持旧统计并明确其历史适用边界，或授权最小统计适配”列为实施前待确认项；本方案不默认扩展页面范围，也不以两个统计混算掩盖冲突。SRF-02 定稿时必须解决，未解决不能宣称完整统计验收通过。

### 6.3 报告快照

新冻结来源追加条目 ID、类型、序号和冻结时的反馈，保留分析正文及代码依据；快照采用明确的新版本，旧冻结来源不改写。`ReportInputService`、`ReportFactsBuilder` 和来源摘要按快照版本解释逐条反馈，事实与意见继续区分，不把人工评价当成程序已经验证的结论。

报告候选、报告来源阅读目前也显示反馈，且只支持旧问题／整份结果结构。需要列出消费者并在 SRF-02 确认最小数据适配范围；已有报告界面的布局保持原样。若展示新条目反馈必须修改其界面，应先取得负责人对这项 tab 外例外的明确确认，不能把新增反馈塞入旧 `resultFeedback` 造成语义错误。只批准结果 tab 时，不能把报告端完整展示记为已交付。

## 7. 工作顺序与验收

状态、依赖和关闭条件统一维护于[主 ROADMAP 的 SRF 工作包](../../../ROADMAP.md#srf-专项审查结果展示与逐条反馈2026-10-27)，本方案不另存一份任务状态。SRF-01 为本轮文档完成；SRF-02 起待负责人明确授权，不自动启动。

| 验收编号 | 验收对象 | 核对内容 |
| --- | --- | --- |
| SRF-A01 | 三类界面 | 与原型信息分区一致，评论直接展示；实际数据无伪造字段，tab 外布局及公共默认展示未被连带改变 |
| SRF-A02 | 独立反馈 | 同一结果两条结论分别准确／不准确，保存、刷新、重新进入后各自保留；跨专项／跨文件不串输入 |
| SRF-A03 | 身份与发布 | 服务端 ID 稳定；合并后序号正确；显示排序不影响关联；发布回滚、重复建索引不留下半成品或变更既有 ID |
| SRF-A04 | 反馈保存保护 | 仅评论、清除评价、保存失败重试、在途再次编辑、两页面版本冲突及迟到响应均保留正确输入 |
| SRF-A05 | 非可反馈结果 | 空结果、未完成、Agent、伪造 ID、错类型、缺失索引均按约定处理；不以顶层总结或依赖事实承载条目反馈 |
| SRF-A06 | 统计 | 三类分别统计，未反馈及无法判断单列，无明确判定显示空值；历史 RESULT 反馈不混入；tab 外统计范围按已确认边界验证 |
| SRF-A07 | 新空库 | 全迁移链创建新表，回填零扫描，新分析产生索引，用户直接反馈并读取成功 |
| SRF-A08 | 已有数据升级 | 多条／零条／重复标题／不同类型／损坏正文／未完成样本；回填可重复，中断后可继续，原正文、历史反馈与旧报告保持原样 |
| SRF-A09 | 新旧报告 | 新快照逐条反馈冻结后不随当前反馈变化；旧快照原样读取；候选和来源展示按已确认范围核对，不更换旧字段语义 |
| SRF-A10 | 代码定位 | 多位置、跨文件辅助证据、修改前后版本与原始行号继续有效；长文本与长路径能阅读 |

单元和组件检查优先覆盖身份、反馈、统计及快照语义变化，不为纯间距样式编写镜像测试。正式构建输出隔离；类型检查若受已有错误影响，记录基线与本次影响，不将失败写为通过。真实模型调用、现有库升级、服务重启及内网部署按后续明确授权对象执行。
