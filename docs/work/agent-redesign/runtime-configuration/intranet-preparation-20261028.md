## 2. 配置应在哪一步准备

1. 在外网逐组审阅[完整参数规范](specification.md)，区分保留值、建议修改值和待确认值。
2. 在外网生成内网版 `config/application.yml`、部署环境模板和业务配置清单。最终文件须与选定版本的参数绑定类一致。
3. 完成 CFG-06 的部署衔接：单库模板、外置配置加载、环境变量传递、配置检查入口和打包范围一致。
4. 用同一产物执行静态配置检查及隔离部署演练，再组装最终离线交付包。
5. 内网填写或注入真实凭据，核对目标地址与资源占用，执行实际业务验证；保留现场配置及版本记录。

运行参数修改通常不需要重建镜像。YAML 修改后重启应用；容器环境变量、内存、端口和挂载修改后重新创建受影响容器。前端运行参数修改后刷新已打开的页面。Agent 冻结预算用于新建任务，重启不续跑旧任务。

## 4. 不能只改模板而遗漏的衔接

- [规范参数样例](application.yml.example) 尚未接入正式部署；当前 `deploy/config/application.yml.example` 仍含旧路线键，不能直接当作新路线完整配置。
- 样例中的 `DB_URL`／`DB_USER`／`DB_PASSWORD` 必须由最终 Compose 显式传入。只写入宿主机 `.env` 不等于容器和应用会读取。
- 当前部署脚本首次生成 YAML 后会保留文件，升级时只补缺失的 Agent 段；只修改 `.env` 或 `.example` 不保证已有 YAML 同步改变。
- 镜像入口尚未显式指定规范拟定的外置配置路径；CFG-06 需验证实际加载文件及覆盖顺序，避免读取到非预期参数。
- 模型地址、模型名称、窗口／输出能力、项目仓库、提示词及版本由管理界面和数据库维护。当前 YAML 中旧 `deepseek.*`／`.env` 的 `AI_BASE_URL` 等入口不能作为新库模型初始化方案。
- 当前公开 Actions 流程会复制 `deploy/` 并发布到公开 Release；真实凭据及需保密的环境信息应独立交付，不混入公开模板、源码快照或自动发布包。

| 场景 | 手册必须说明的内容 |
| --- | --- |
| 首次部署 | 解压与完整性校验、配置填写、镜像导入、空库初始化、启动、就绪判断、访问地址及失败处理 |
| 日常启停 | 可复制的应用与整套服务启动／停止／重启命令；停机前运行任务的处理；操作顺序、状态与日志检查；YAML 修改和容器环境变更的生效方式区别 |
| 新版本保留数据升级 | 支持的起始版本、固定数据目录与配置的保留方式、维护窗口、停止写入、备份与恢复核对、镜像及脚本更新、配置增补、自动数据库结构升级、升级后业务与数据验证、失败处置与回退 |

保留数据升级须满足以下约束：

- 数据目录不得随版本包切换而隐式指向空目录；不得把删除数据库目录或清空数据作为普通升级步骤。
- 同一新路线的表结构变化由经过验证的增量迁移处理，保留已有迁移记录。每次发行说明支持的升级来源、迁移内容、预计停机影响及不可逆变化；不能承诺任意历史版本都可直接升级。
- 备份范围包含实际业务库、外置 YAML 和 `.env`。升级封存副本须独立于自动清理的日常备份，并核对恢复可用性。
- 数据库迁移失败时停止升级，保留日志与现场。只有旧程序兼容升级后结构时才可只回退镜像；需要恢复数据库时使用明确版本的已核对备份，并说明升级后新写入数据的处理和可能丢失范围。
- 本次从 9 月旧路线切换到新路线的「独立新库部署」，与今后新路线内的「保留数据增量升级」分别编写。新库部署不会自动转换旧库业务记录；如要求保留并转换旧记录，另行制定数据迁移方案。
- 出包前分别演练空库部署、日常启停和有数据升级。手册只将实际执行通过的步骤标为已验证。
