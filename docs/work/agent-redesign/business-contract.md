# 专项审查与 Agent 分析业务契约

日期：2026-10-19（Asia/Taipei）。版本：讨论整理版。目标分支：`refactor/agent`。

本文以负责人在本次会话中的思考和明确决定为主要来源，供后续逐项确认、需求细化和 ROADMAP 编制使用。已定业务方向、待确认细节和助手建议分别标明；本文不表示功能已实现，也不授权整批迁入旧分支代码。

配套阅读：[refactor/review 成果盘点](review-inventory.md)。盘点中的候选能力均需逐项确认后才能进入实施范围。

## 1. 重新设计的出发点

从实际使用出发，先回答三个问题：希望系统完成什么任务；是否知道需要交给系统哪些材料；是否需要系统根据中间发现继续调查。现有分析器、审查模式和内部阶段作为实现参考，不直接决定新的产品分类。

负责人提出的任务包括：发现代码问题、解释业务问题、分析类之间的耦合度、分析设计模式。材料范围可能尚不明确，也可能明确到一个文件、多个文件或文件中的某一行。系统应支持范围明确的常规分析，以及通过多轮交互寻找材料、继续分析的 Agent 方式。

本轮采用两条业务路线：

| 路线 | 主要用途 | 负责人确定的边界 |
| --- | --- | --- |
| 专项审查 | 问题审查、耦合度分析、设计模式分析 | 保持简单、稳定，主要改善材料准备；复杂调查转入 Agent |
| Agent 分析 | 开放的业务问题、复杂关联分析和更高自主性要求 | 用户描述诉求，系统与 LLM 多轮交互，通过基础工具寻找和读取材料，形成结果 |

两条路线不要求用户先掌握分析器与 `STANDARD`、`CONTEXT_ONLY`、`VERIFIED` 的组合。现有三模式的界面退出方式及历史记录展示，属于后续兼容设计事项。

## 3. 专项审查的业务契约

### 3.1 输入与结果

| 任务 | 用户主要输入 | 结果的业务重点 | 复杂情况的去向 |
| --- | --- | --- | --- |
| 问题审查 | 审查范围、通用规则或追加重点 | 发现的问题、文件名和行号；必要的原因及建议 | 需要跨文件持续补证或解释业务原因时，转入 Agent |
| 耦合度分析 | 待分析范围 | 类或模块关系、耦合指标及解释 | 深入追查业务边界、架构原因或重构影响时，转入 Agent |
| 设计模式分析 | 待分析范围 | 模式分析及其说明 | 复杂模式关系、业务适用性或进一步设计讨论，转入 Agent |

上述结果字段是业务描述，不锁定旧 schema 或旧页面。指标算法、模式分类与报告结构是否沿用，按盘点逐项确认。

### 3.2 材料增强

专项审查在准备材料时，可以附加直接相关的类型声明、接口契约或其他必要背景。增强是常规能力，重点是让本次任务获得足够材料，不把专项审查扩展成开放式仓库调查。

「分析目标」与「辅助材料」应能区分。例如，目标是一行或一个方法，辅助材料可以包含其所属类型。行范围的选择交互、允许读取的边界、具体材料种类和读取上限仍待确认，不在本文直接规定数值。

用户选多个文件，不自动等同于把所有文件合并成一个模型请求。专项是否提供相关文件联合审查，以及哪些场景交给 Agent，见第 8 节待确认项。

### 3.3 提示词组织

采用本次讨论中已解释的职责划分：基本审查要求、用户追加重点、输出格式要求，加上本次代码与辅助材料。没有自定义提示词时，仍应有基本任务指令；自定义重点用于表达项目要求。

系统基本指令与输出协议如何在新路线中固定、各任务最终采用什么 schema，属于后续技术契约确认。不要把 `refactor/review` 目前的候选核验字段和三模式元数据直接当作新产品必填内容。

### 3.4 一次分析与复杂问题

专项采用预先准备材料、执行分析、汇总结果的方式。内部可以有多个请求；「一次分析」不承诺只有一次 HTTP 调用，也不代表已经并行执行。

不保留强制逐候选多轮语义核验。文件和行号用于定位，问题解释用于说明模型判断；这些信息不自动代表人工确认。路径、行号、结果结构等基本有效性检查与语义核验有不同目的，具体检查范围在实现设计时确认。

发现复杂线索或材料不足时，结果应如实说明边界，允许用户继续进入 Agent 分析。自动带入原问题和已有材料是助手建议，接续方式与用户操作尚待确认。

### 3.5 分块的方向与待决点

容量管理应考虑完整请求：基本指令、用户重点、输出格式、代码和辅助材料，并预留输出容量。文件是否需要拆分，与编码规范是否推荐拆分类文件是两件事。

当前 `refactor/review` 存在初始字符上限和完整请求容量两道限制，具体事实见盘点 B-03。固定 `窗口 / 8`、UTF-8 字节估算、输出预留以及按行拆分都属于待评估实现，不是本业务契约批准的参数。

助手建议先尝试完整业务单元，再依据完整请求容量决定是否拆分，并优先采用语义边界；负责人尚未逐项批准该算法。并行执行可能影响耗时，但不预先承诺并行数或提速比例。

## 4. Agent 分析的业务契约

### 4.1 任务与过程

用户直接表达诉求，可提供明确材料，也可只提供问题线索。Agent 围绕目标决定下一步需要什么材料，调用工具读取后继续分析，最终形成回答。多轮交互由中间发现推动，区别于固定重复提示词或格式修复。

业务解释、复杂问题调查、复杂耦合或模式分析，以及专项审查无法在简单流程内完成的深入分析，统一由此路线承接。

### 4.2 基础工具边界

| 工具 | 业务用途 | 当前决定 |
| --- | --- | --- |
| 仓库树 | 了解目录和模块结构，寻找可能相关的材料 | 纳入基础工具方向 |
| `glob` | 根据路径和文件名模式定位文件 | 纳入基础工具方向 |
| 获取内容 | 读取分析所需的源码或其他仓库内容 | 纳入基础工具方向；范围、分段、批量和返回格式待设计 |
| `grep` 或内容检索 | 根据内容定位符号和业务关键词 | 首版不提供无缓存的全仓内容扫描；有缓存时可再讨论启用 |

工具面向材料读取；本轮讨论没有批准修改被审仓库、执行其构建脚本、自动修复或发布外部评论。Agent 框架、原生工具调用与普通 JSON 协议的选择均未确定。

### 4.3 结果与停止

结果应围绕用户诉求说明结论和依据，证据可以跨多个文件；材料不足时说明尚不能回答的部分。用户不需要先选择旧核验状态或理解内部阶段名称。

停止条件、调用及时间预算、取消与恢复、是否向用户追问、是否支持结果后的连续对话，以及 Agent 的最终结果格式，仍需专门确认。本文不沿用旧模式的固定轮数或预算数值。

## 5. 人工反馈与评论

问题审查允许人工针对具体问题反馈准确度并发表评论。设计模式和耦合度分析允许人工针对报告反馈准确度并发表评论。这是负责人指定的新反馈方向。

「报告」在此表示对应分析的报告或结果载体，是否直接复用现有综合报告实体需要确认。准确度标签或评分、评论是否独立于评分、编辑与历史保留、多人意见以及统计分母均未锁定。

问题级判断与报告级判断分开记录。未反馈不能自动作为正确，采用建议也不自动等于判断正确；现有 truth/action 双维界面和版本冲突机制是否完整保留，按盘点确认，不因代码已存在就一并采用。

不保留 `STANDARD / CONTEXT_ONLY / VERIFIED` 的效果对照流程。取消该对照需求不等于取消软件功能测试；本文不把旧 E1–E3、precision/recall 对照门槛重新列为新路线的实施要求。原项目外部验收指标与新反馈口径的关系另行确认。

## 6. 发起表单与页面组织

审查通过独立发起表单组织参数，避免把配置长期平铺在代码浏览或结果页面。负责人已认可 `refactor/review` 的这一交互方向，但没有批准照搬其中的三模式选择、全部预算项或历史配置说明。

报告生成同样移入独立表单。这是本次新增的明确方向；旧分支已有生成确认弹窗，不等于已经完成生成表单迁移。报告选材、名称、模型、提示词等字段是否保留及如何排列，需要逐项设计。

专项与 Agent 的入口命名、菜单数量、是否共用表单，以及项目入口和全局入口的关系仍待确认。助手提出的「四个任务入口」只是建议，不作为已批准页面结构。
