## 1. 重新设计的出发点

从实际使用出发，先回答三个问题：希望系统完成什么任务；是否知道需要交给系统哪些材料；是否需要系统根据中间发现继续调查。现有分析器、审查模式和内部阶段作为实现参考，不直接决定新的产品分类。

负责人提出的任务包括：发现代码问题、解释业务问题、分析类之间的耦合度、分析设计模式。最初讨论的材料范围包括一个文件、多个文件或文件中的某一行。本轮进一步明确：专项审查仅提供文件级目标选择；方法、行等更细目标以及材料范围尚不明确的调查需求交给 Agent。

本轮采用两条业务路线：

| 路线 | 主要用途 | 负责人确定的边界 |
| --- | --- | --- |
| 专项审查 | 问题审查、耦合度分析、设计模式分析 | 统一逐文件分析，多选时批量执行，保留有限材料增强 |
| Agent 分析 | 开放的业务问题、模块级与联合分析、更细目标及更高自主性要求 | 用户描述诉求，系统与 LLM 多轮交互，通过基础工具寻找和读取材料，形成结果 |

两条路线不要求用户先掌握分析器与 `STANDARD`、`CONTEXT_ONLY`、`VERIFIED` 的组合。保留代码浏览与审查中心，专项与 Agent 共用发起表单外壳、分别展示适用字段。旧入口关闭，旧试运行记录及报告封存，不在新产品中提供历史读取兼容。

两条路线执行完成后均产生「审查结果」。Agent 的结论及 Markdown 正文同样属于审查结果，不直接作为已经生成的报告。用户另行勾选专项及 Agent 审查结果，通过独立表单生成报告。下文涉及模式、耦合分析的结果级反馈，均指相应审查结果，不指该独立生成的报告。

外部 API 接入目前是预留能力，尚未实际使用。保留 `dev` 已有实现，本轮暂不扩展，也不为该预留能力增加新的配置和交互。它作为外部工具接入保留，不套用 LLM 专项的提示词规则；出现实际使用场景后，再明确外部审查的触发范围、结果获取和展示要求。

### 3.2 材料增强

专项审查常规补充与目标文件有关的必要声明和契约。首版自动增强限定在当前仓库内可取得的材料，辅助材料与目标文件使用同一提交版本。该能力按需补充背景，不扩展成开放式仓库调查，也不承诺补齐全部依赖。

「分析目标」与「辅助材料」应能区分。例如，目标是一份文件，辅助材料可以包含相关接口的声明。辅助文件仅提供背景，不自动成为审查目标。专项不提供方法或行范围选择，但程序可以读取相关声明片段来准备背景。

所有专项选择多个目标文件时，按文件分别准备材料并执行批量分析，不把这些目标合并为联合分析任务。以多个文件或模块作为整体目标的分析需求，统一交由 Agent。

批量分析仍允许为单个目标文件补充有限的相关背景，例如其他文件中的接口声明；辅助材料的存在不等于多个目标被联合审查。该边界同样适用于耦合度和设计模式分析。文件级结果按实际材料给出结论，不作为完整模块或全仓结论；具体指标、结果结构与批量展示方式仍待细化。

| --- | --- |

#### 3.2.2 Java 继承声明查找

采用程序控制的有界查找，基本流程如下：

1. 使用 JavaParser 解析目标源码，提取包名、导入、`extends` 和 `implements` 等声明信息。
2. 使用当前仓库同一提交版本的文件路径清单寻找候选，结合限定名、导入和同包信息缩小范围；读取候选后核对包名与类型声明，不能只凭文件名相同就认定匹配。
3. 对已定位的父类或接口继续解析其父类型。父类链和接口分支均受访问去重及资源限制约束，遇到无法可靠定位的类型时停止相应分支。
4. 从已取得的源码提取继承关系、必要声明、候选成员签名、注释与来源位置，作为目标文件的辅助材料；不把所有祖先类全文默认加入请求。
5. 路径清单和已读源码可缓存复用，缓存须区分仓库与提交版本；查找不以每次全文扫描仓库作为常规前提。

现有结构抽取能够读取继承名称和方法签名，但完整的定位、遍历及材料摘要能力仍需建设；旧上下文候选检索不能直接认定为完整继承解析器。

本方案查找继承声明，提供可定位的父类契约及候选成员，不承诺完成编译器级的符号解析。泛型、重载、复杂覆写等情况不能仅凭名称匹配就宣称已找到准确的方法声明，更不能据此认定运行时的实际实现。引入 JavaSymbolSolver、完整 classpath 等更强解析能力不在本次批准范围内。

#### 3.2.3 资源限制、资料缺失与第三方依赖

继承深度、辅助文件数、读取量和材料容量均由系统运行配置统一管理，优先保留目标文件及必要声明。具体数值由后续技术方案提出，并以实际仓库验证，不增加发起表单参数。重复访问、定位歧义、解析失败、源码不可取得或额度耗尽时，停止相应查找并保留未解析状态，不将其解释为类型不存在或没有问题。

第三方类可能只有 API 文档、类型签名或依赖包，也可能完全没有可用资料。可靠资料可以帮助理解可见契约，但签名本身不能说明内部实现、幂等性或其他未明确约定的行为；LLM 对某个库的印象也不能代替对应版本的依据。

首版不自动下载依赖或源码包、解析 JAR、反编译或获取外部文档。已有的用户补充说明仍作为任务背景使用，不因此新增外部资料抓取能力。需要这些额外能力时另行确认。

辅助资料缺失时，可以依据已取得的目标代码继续分析；涉及未知契约的部分应保留判断边界，不自行补造依赖行为。转入 Agent 同样不保证取得缺失源码或回答所有问题，仍受可访问资料限制。

### 3.3 提示词组织

所有专项审查统一采用以下提示词职责划分：

> 提示词 = 内置默认指令 + 策略提示词（可选）+ 针对文件的补充说明（可选）+ 程序内置输出协议

| 组成部分 | 来源与职责 |
| --- | --- |
| 内置默认指令 | 由程序按专项类型提供，定义基本任务和审查要求；没有用户补充时仍可执行 |
| 策略提示词（通用补充规则） | 随选用的审查策略带入，表达可复用的项目规范或关注重点；不另设本次审查的临时统一提示词 |
| 针对文件的补充说明 | 用户在本次审查中按目标文件分别填写，每个文件一份可选说明，表达该文件的背景、约束或关注点；差异审查中的修改意图是其一种用途 |
| 程序内置输出协议 | 由程序按专项类型规定结果结构，两类用户补充内容均不替换该协议或内置默认指令 |

代码及辅助材料与上述指令共同构成完整输入。通用规则不替代本次文件说明，文件说明也不回写通用规则配置。文件说明随本次审查记录保留，供回看与调优，不自动保存成公共模板；具体持久化方式留待设计。

临时补充只做到文件级，不增加任务级或提交级统一说明。选择三个文件时，可分别填写三份说明，也可留空；审查某个文件时仅带入该文件的说明，拆分后各片段继续携带所属文件的说明。该规则不改变所有专项逐文件批量分析的边界。

大段或可复用内容建议配置到审查策略的提示词中，而非临时追加。此处不新增强制字数阈值；具体输入控件与保存方式仍待设计。

各专项的完整指令、具体 schema 和表单交互仍待细化。不要把 `refactor/review` 目前的候选核验字段和三模式元数据直接当作新产品必填内容。

#### 3.3.1 冲突优先级

按以下规则组织提示词，并在同一次审查中由 LLM 遵循：

1. 内置默认指令与程序内置输出协议优先，用户补充不能改变基本任务或返回格式。
2. 文件补充说明优先于选用的通用补充规则，允许表达具体文件的例外和要求。
3. 没有冲突的要求共同生效，不能因填写文件说明就丢弃整份通用规则。

例如，通用规则要求「不允许重试」，文件说明明确「这个文件允许重试，重点检查是否重复处理」，则在不违反内置要求的前提下，采用文件说明中的具体要求，其余适用的通用规则继续生效。

系统不增加单独的 LLM 调用或语义核验流程来识别提示词冲突。隐蔽冲突导致的遗漏、偏离预期或质量下降，不作自动检查，由用户调整提示词和人工反馈。

#### 3.3.2 输出协议失败处理

程序检查返回是否符合固定输出协议，例如 JSON 是否可解析、必填字段及类型是否合规。初次返回不符合时，最多额外重试 2 次；次数耗尽直接失败，不通过返回原始文本或忽略协议来记为成功。每次错误及实际调用内容均须记录。该次数由本轮 D-42 确认，不是直接继承旧分支数值。

重试依据是可观察的输出协议错误，不要求先判断错误是否由提示词冲突引起。协议重试不构成问题真伪核验或审查质量复查；结构合规也不表示审查结论一定符合用户预期。上下文超限等其他错误仍按各自规则处理。

#### 3.3.3 提示词留存与完整内容查看

用户应能查看本次实际组装发送的完整提示词，包括内置默认指令、选用的通用规则、适用的文件说明、输出协议，以及作为消息内容发送的目标代码和辅助材料；不能只提供通用模板正文或版本号作为完整提示词。

本次文件说明及实际使用的完整提示词随审查记录保留。后续修改策略提示词，不改变历史记录中的输入内容；「临时」表示仅对本次任务生效，不表示执行结束后丢弃。临时说明不自动生成公共模板。

实际输入快照按任务、文件、片段及调用次数组织，拆分与重试涉及多次调用时，可以定位到对应输入及错误。默认先展示审查结果，用户按需展开完整调用内容；具体存储结构和阅读组件由后续设计确定。

`refactor/review` 已有提示词模板及版本查看、快照信息和长内容阅读等部分能力，可逐项评估复用；本项业务确认不等于批准整套旧界面迁移，也不表示来源已经完整实现实际调用提示词回看。

### 3.4 一次分析与复杂问题

专项采用预先准备材料、执行分析、汇总结果的方式。内部可以有多个请求；「一次分析」不承诺只有一次 HTTP 调用。容量导致的文件拆分须由「智能拆分文件」开关允许，不能由内部字符阈值自行开启。

不同目标文件允许并行分析，智能拆分产生的片段也受同一并发控制。系统统一限制同时执行的请求数，具体上限作为运行配置，后续按模型服务的承载能力确定；用户发起审查时不配置并发参数。并行仅调整调度，不增加审查轮次，也不将文件或片段改为联合分析。

各文件独立记录结果和失败，一个文件失败不使其他文件的成功结果丢失。批量任务清楚展示完成、失败及未完成范围，不能将部分完成呈现为整批成功；片段失败对所属文件状态的具体投影由技术设计明确。

不保留强制逐候选多轮语义核验。文件和行号用于定位，问题解释用于说明模型判断；这些信息不自动代表人工确认。路径、行号、结果结构等基本有效性检查与语义核验有不同目的，具体检查范围在实现设计时确认。

### 3.5 文件完整性与智能拆分

审查以保持业务功能及上下文完整为优先目标，先保留完整文件。文件是否需要拆分，与编码规范是否推荐拆分类文件是两件事；不为了增加并行度而默认预切分。

发起专项审查的表单增加「智能拆分文件」开关，控制是否允许拆分目标文件。

| 开关状态 | 已确认的行为 |
| --- | --- |
| 未勾选 | 保持目标文件完整提交；LLM 返回上下文超限时直接报错，不自动拆分文件后重试 |
| 已勾选 | 仍优先整文件分析；容量不足时才允许执行下述辅助材料精简与文件拆分流程 |

开关初始默认关闭。用户可以显式复制历史参数，新任务仍重新确定版本和配置；不能把未勾选解释为允许静默拆分。

允许智能拆分时，容量判断以实际完整请求为对象：内置默认指令、选用的通用补充规则、针对文件的补充说明、输出协议、目标代码、辅助材料及请求封装均计入输入，并预留输出预算和安全余量。

完整请求 token 估算优先采用对应 tokenizer；无法取得时保守估算。输出预算、安全余量及允许的容量处理次数集中配置，具体数值由技术方案提出并验证；容量处理次数有上限，不进行无限重试。

> 可用输入容量 = 上下文窗口 − 输出预算 − 安全余量

按以下顺序处理：

1. 整文件与辅助材料符合完整请求容量时，保持整文件分析。
2. 预估超限时，先压缩或移除低优先级的可选辅助材料，再判断容量；不通过删除用户规则或输出协议来腾出空间。
3. 仍然超限时，才拆分目标代码，尽量保留相关业务单元，优先采用类型、方法等语义边界。
4. 单个业务单元或方法仍然超限时，再拆为更小片段，并保留必要的所属类型和位置等背景。
5. 每个片段继续携带适用的规则、文件补充说明、输出协议和必要上下文；结果仍归属原文件。

勾选后，实际 LLM 上下文超限也允许进入容量处理和拆分；容量估算不能保证与模型端计算完全一致。其他调用错误不作为文件拆分的理由。错误识别及允许的处理次数仍需技术细化。

文件拆分定位为容量不足时的轻量兜底，不为超长文件建立复杂的跨片段业务还原机制。分段审查保留必要背景，结果由程序汇总，不增加额外的 LLM 整体复查或综合分析。

- 每个片段附带必要的所属类型、字段、相关方法签名与注释，以及已取得的必要辅助契约；规则、文件说明和输出协议按适用范围保留，全部内容仍计入容量。
- 程序将片段结果归回原文件，保留原始位置及来源片段，以文件、位置和问题类别为基础对能够确认重复的问题或条目去重；具体匹配规则在实现时细化。
- 不承诺分段审查与整文件审查等效，不通过额外多轮分析弥补所有跨片段关系。容量允许时仍优先完整文件。

当前 `refactor/review` 的两道限制作为盘点事实保留，见 B-03；新路线取消固定「上下文窗口 / 8」作为预切分依据。估算、语义分块、位置保留与去重方向已经确认；具体 tokenizer 适配、预算数值、边界识别、最小片段、错误识别及并发上限由技术设计细化，不把旧 UTF-8 字节估算或字符阈值直接列为新要求。

### 3.6 差异审查的目标

差异审查默认发现本次变更引入的问题，并检查变更是否符合所选审查规则。结果中的问题应与此次变更有关；删除代码也可能引入问题，不要求问题必须落在新增行。辅助材料中与变更无关的历史问题不自动算作此次变更的问题。

修改前后代码及必要背景用于判断改动影响，阅读范围可以大于变更范围。commit message 用于辅助理解；缺失或含糊不阻止代码问题审查，也不能据此自行补出完整业务需求。

用户可以通过文件补充说明表达修改意图及明确约束。专项可据已有材料指出代码与约束的冲突；完整追查业务意图是否实现，属于深入分析诉求，交由 Agent 讨论和处理，不因提供说明就成为专项的默认承诺。

差异审查在产品中归为问题审查的范围选择。用户先选择问题审查，再选择文件内容审查或提交差异审查；两者均以文件作为目标选择粒度，系统根据范围采用相应的默认指令并准备材料。具体菜单、底层分析器是否合并及输出定位字段仍待设计。

## 4. Agent 分析的业务契约

### 4.1 任务、范围与代码版本

用户通过表单发起 Agent 任务，输入收敛为「审查范围」和「审查要求」，目的与要求合并。范围可以用文字描述，也可以通过已有树形结构选择文件或范围，或者选择多个提交。审查要求必填；首版文件与提交选择互斥，文字可补充说明。具体字段与布局见第 6 节。

所选范围是分析目标，不是辅助材料的读取边界。Agent 可以读取当前仓库内范围外的相关文件作为背景；背景文件不自动成为审查目标，也不因取得这些材料就把结论扩大为全仓审查。

发起时固定任务所需的提交版本，执行中不跟随远端新提交移动。读取、搜索、diff 和结果引用均须能追溯到对应版本；修改前后材料分开标明，不能用最新分支内容替代已经固定的旧版本。版本解析和工具访问校验由系统控制。

业务解释、复杂问题调查、以多个文件或模块作为整体目标的耦合或模式分析，以及专项审查无法在简单流程内完成的深入分析，统一由此路线承接。模块级分析归入 Agent，不因其可以采用固定计算流程而重新设为专项任务。

### 4.2 多提交分析

默认读取每个所选提交的差异，由同一个 Agent 围绕用户要求综合分析。支持选择非连续提交，不把最早与最晚提交之间的全部变化自动当作用户所选范围，也不默认以最终净变化替代各次提交的差异。

合并提交默认与第一父提交比较，结果及差异查看需要明确展示比较关系。各次差异对应的修改前后代码、辅助材料及证据使用各自版本，不将全部材料强行归入单一最终版本。

根提交、二进制内容、大差异和同一文件跨多次提交的展示细节，由后续技术设计处理，不重新开放上述多提交业务语义。

### 4.3 统一管理的只读工具

| 工具 | 业务用途 | 已确认的边界及后续设计 |
| --- | --- | --- |
| 仓库结构与文件信息 | 了解目录和模块结构，寻找可能相关的材料 | 纳入统一工具管理；展开深度、分页和概览结构由技术设计确定 |
| 文件搜索 | 根据路径、文件名或 `glob` 模式定位文件 | 纳入统一工具管理；不与内容搜索混为一种查询 |
| 代码搜索 | 根据内容定位类型、方法名和业务关键词等线索 | 首版采用受限 git grep 和版本化缓存，复用本地镜像；具体约束见第 4.9 节 |
| 代码读取 | 读取已定位的源码或其他仓库内容 | 纳入统一工具管理；按实际需要设计范围、分段、批量和返回结构 |
| diff 查询 | 查看所选提交及相关代码变化 | 遵循第 4.2 节的逐提交及第一父提交语义，支持继续定位具体文件和差异 |

独立设计适合 LLM 的只读工具契约，不直接复制前端树控件、文件浏览或提交选择接口的返回结构。工具定义、参数校验、调用入口、返回及错误约定统一管理；返回内容能够识别版本、位置和结果完整性，不将截断、超时或读取失败解释为不存在。

按所用模型能力适配调用协议，首版采用简单的「LLM 决定下一步 → 系统调用工具 → 返回材料 → LLM 继续」执行循环。具体工具名、参数、返回字段、协议适配及管理实现由技术设计确定。

工具面向材料读取。本轮不包含修改被审仓库、执行其构建脚本、自动修复或发布外部评论的能力。

### 4.4 指导提示词及组装优先级

专项审查使用策略，Agent 模式使用提示词。Agent 复用现有提示词管理能力并区分用途；用户可选一份指导提示词，未选择时系统仍提供默认调查指令，不要求用户选择专项审查策略。

指导提示词保存可复用的调查步骤及项目导航知识，以文本指导工作。本轮不建设 Skill 的发现、渐进式披露、动态加载或脚本执行机制。此处限定的是被审系统的 Agent 产品能力，不改变开发工作区已有 skills 的使用规则。

Agent 的输入包含内置默认调查指令与边界、可选指导提示词、本次范围与审查要求、工具说明及输出约定，并在执行中加入工具返回的材料。冲突优先级如下：

1. 程序内置边界与输出约定优先。
2. 本次审查要求优先于可复用的指导提示词。
3. 无冲突的内容共同生效。

提示词提供方法与线索，实际定位、读取和 diff 查询仍通过工具执行。项目导航描述须结合实际版本的代码核对，不能直接当作源码证据。具体存储、组装消息及用途区分方式由技术设计确定。

### 4.5 执行、完成条件与硬限制

用户提交后，Agent 在内部多轮调用 LLM 和工具，不在执行中追问用户。需求含糊或资料不足时，在审查结果中说明理解、假设及缺失信息；需要补充要求时，由用户另行发起任务。

提示词要求避免无休止调查。程序设置以下结束规则：

| 条件 | 行为 |
| --- | --- |
| 已按任务要求形成现有材料支持的结论，并满足完成条件 | 结束调查，保存审查结果 |
| 材料不足，现有依据无法支持进一步结论 | 明确记录已取得依据及尚不能回答的部分，不宣称已经排除问题 |
| 达到调用次数上限、时间上限或额度上限 | 立即终止任务并说明命中的限制，不继续调查或绕过上限 |
| 达到上下文容量阈值或模型端返回上下文超限 | 按第 4.6 节终止并说明容量限制，首版不提供压缩后继续 |
| 关键步骤失败，无法继续执行任务 | 明确失败及原因，保留必要执行记录 |

调用、时间和额度均为硬限制。完成信号按第 4.11 节采用显式「提交结果」动作；具体计量口径、上限数值及状态字段由技术设计确定，不沿用旧模式的固定轮数。结束状态须区分正常完成、材料不足、命中限制及失败，不将已有部分记录冒充完整成功结果。

暂态错误有限重试，重试计入总预算；可替代材料缺失时可以继续调查，关键步骤失败时明确结束。单次重试次数及错误分类由技术设计确定，不因缺失材料而无限重试，也不将工具错误解释为没有相关代码。

### 4.6 上下文容量与超限终止

按 D-67，首版不压缩 Agent 上下文，也不提供手动压缩后继续执行的功能；不通过自动摘要或丢弃较早代码延长任务。该规则针对 Agent 的多轮会话，不改变第 3.5 节已经确认的专项文件拆分及辅助材料处理规则。

下一次调用前，根据实际模型窗口及完整请求容量检查上下文占用。达到窗口一定比例的容量阈值时终止任务，说明命中的容量限制，保留已保存的输入、执行记录及已有结果，不将其呈现为完整成功。阈值为请求封装、输出及安全余量预留空间，具体比例和估算方法由技术设计确定。

若模型端实际返回上下文超限，同样终止并说明错误，不自动压缩或反复发送同一请求，不保持等待用户压缩的暂停状态。

需要继续分析时，由用户按第 4.7 节另建任务并重新确定版本与配置，不恢复原会话。原任务保留实际已消耗预算及停止原因，不通过继续原任务重置限额。

具体阈值、估算方法及终止状态留待设计；首版不建设会话压缩、等待用户压缩及压缩后继续的状态与存储流程。

### 4.7 审查结果、留存与后续分析

Agent 产出审查结果，采用少量固定信息加 Markdown 正文，围绕用户诉求说明结论、依据、分析边界及文件位置，证据可以跨多个文件。不强行套用专项的问题列表；材料不足时说明尚不能回答的部分。

保存本次范围、审查要求、所用指导提示词及实际组装输入、仓库版本、模型、必要执行记录和最终审查结果。实际调用按任务及调用次数组织；涉及不同文件、片段或重试时能够区分。具体输出字段及存储结构由技术设计确定。

完成后的审查结果固定保存，不通过继续对话改写已有结论。进一步分析另建任务并引用旧审查结果；新任务重新确定版本与配置，旧结论不自动成为新版本代码的事实。用户若要形成报告，需另行勾选专项及 Agent 审查结果，按第 6.4 节生成。

### 4.8 进度、取消与普通中断

执行中展示正在执行的动作及已经查阅的范围，允许用户取消。普通中断后，通过新任务重跑，首版不恢复原会话；上下文容量限制同样按第 4.6 节终止，需要继续分析时新建任务。

进度用于说明可观察的工具执行及材料范围，不要求用户理解旧候选核验阶段或模式状态。具体展示及取消后的状态处理由技术设计确定。

### 4.9 大仓库检索方案

本轮表格第 7 项经补充规模和专项讨论后，负责人已批准首版采用「本地镜像 + 受限 git grep + 版本化缓存」，暂不引入独立索引服务。该业务选型不表示现有镜像类已经实现 Agent 检索工具，仍需按统一工具契约建设。

规模依据：负责人补充，内网最大项目有 2894 个文件，本地仓库约 170 MB。该数据是项目规模信息，不是搜索性能实测；不能将本地仓库占用直接视为每次搜索的文本量。

| 环节 | 已批准的首版规则 |
| --- | --- |
| 仓库准备 | 复用共享本地镜像，任务准备时按需同步并固定提交；每次搜索复用本地材料，不逐次经远端下载文件 |
| 文件定位 | 缓存对应提交的路径清单，通过文件名、目录及 glob 定位候选 |
| 内容搜索 | 在指定提交上执行受限 git grep，支持目录及文件类型过滤，返回路径、行号及简短上下文；不遍历全部提交历史 |
| 查询缓存 | 按仓库、提交版本和查询条件缓存，避免重复搜索；不同版本不能误用同一结果 |
| 资源控制 | 同时限制搜索并发、工作线程、执行时间和返回量，明确标记结果是否完整，截断或超时不能解释为查遍全仓 |

具体同步调度、缓存容量及有效期、过滤和匹配参数、线程数、并发数、超时及返回上限，由技术设计确定，并在目标环境验证搜索耗时及承载。工具仍遵循第 4.3 节的版本、位置和完整性约定。

统一工具接口保留替换底层检索实现的能力。后续若实际出现检索瓶颈，再依据实测另行决定索引方案，不因此将独立索引服务自动加入首版。

| 范围 | 已确认的取舍 |

### 4.11 P33 执行循环与显式结果提交

2026-10-22，负责人按 D-89 确认以下设计方向。模型负责选择调查方向，程序负责工具权限、固定版本、预算、调用记录及结果发布；本节是 P33.1 的设计依据，不表示已启动实现或批准 Agent HTML 原型。

每轮模型响应表达两类动作之一：请求只读工具，或显式「提交结果」。程序校验工具请求后执行、保存实际返回材料并交给下一轮模型；收到结果提交后校验结构及引用，通过后固定保存并结束。首版每个任务内串行执行工具，执行前检查取消、期限和预算；不同任务继续受公共并发控制。

模型协议优先验证目标模型的原生工具调用，实际验证须覆盖「模型请求工具 → 系统回传材料 → 模型继续回答」。专项 JSON 探针不能代替此验证。内部动作和工具管理保持统一；是否需要 JSON 动作协议兼容方式，依据实际模型验证决定，具体工具名和字段名在 P33.1 细化。消息角色、工具调用标识和返回适配继续接入统一组装与公共调用能力。

工具返回须带可核对的版本、路径、原始位置及完整性信息，区分无匹配、部分返回和执行失败。模型选择当前任务已固定的版本标识，程序解析并校验实际 SHA 与所属仓库。读取材料使用稳定引用标识，保存模型实际收到的内容；结果引用须能打开当时材料，多提交材料继续关联各自比较关系，不用最新源码替代。分页和单次返回量可以受限，已进入会话的历史不通过丢弃或摘要延长任务。

「提交结果」包含回答情况（已回答或材料不足）、Markdown 正文、证据引用及未解决事项。程序校验结构和引用是否有效，不自动判断结论的语义真伪；单次模型响应结束标记不作为整个任务完成的充分条件。结果正文说明结论、依据和分析边界，完成后按第 4.7 节固定保存。

执行结束情况与回答充分程度分别记录：模型正常提交且明确说明材料不足，可以形成完整调查记录。负责人已按 D-90 确认这种完整结果允许报告选材，候选及冻结来源保留材料不足标识和未解决事项。命中硬限制、失败或取消时只保留过程与已有内容，不冒充完整成功，也不进入完整结果选材。

P33.1 按 D-90 使用数据库中的实际项目验证，接口与本地命令使用同一固定 SHA 对照，不能用当前工作区的移动版本代替。首版使用 DeepSeek，不使用 Qwen；预算由实验确定，内网场景不以节省调用费用为目标，继续保留容量、期限、调用和资源硬限制防止失控。具体参数与实验边界见 P33.1 设计及验证记录。

每次模型调用、工具执行及结果发布前检查适用的取消、期限和预算限制，所有重试纳入相应预算。上下文计量覆盖工具定义、全部历史消息、工具返回、输出预留及安全余量；命中硬限制后直接终止，不追加总结调用。具体数值、重试口径和状态字段仍在 P33.1 细化。

P33 先以一个固定文件任务验证真实工具调用、继续调查、结果提交和证据阅读，再补齐搜索、多提交及异常边界，最终进行专项与 Agent 混合报告真实联调。HTML 原型覆盖发起、执行进度、调用记录、结果与终止展示，明确区分正常完成、材料不足和命中限制；进度只展示实际动作及已查范围，不虚构完成百分比。

| UPI-B07 | 不为调整前试运行任务建设版本恢复、旧策略请求解析、历史批量迁移等兼容层。旧结果及调用若能原样读取可保留，不能作为必须专门适配的验收条件；旧请求不能静默丢弃策略后继续执行。 |
| UPI-B08 | 策略退出不删除模型、项目和提示词资源。实际数据清理、重建或在途任务处理须在实施时明确对象和步骤，本轮不执行。全新内网环境初始化及调整后新数据闭环是部署验收重点。 |
| UPI-B09 | 模型仍被未完成的审查任务或报告引用时，拒绝删除并提示等待执行结束；已完成任务的配置快照及历史结果保留，不因历史引用永久禁止删除模型。此规则依据负责人要求修复 UPI 审核中的模型删除问题补充。 |

### 9.3 报告通用规则

### 11.2 已确认业务规则

| 编号 | 规则 |
| --- | --- |
| SRF-B01 | 专项结果以明确的总结性结论开头，明细按卡片分区；问题说明、建议、位置和辅助证据可辨认。内部输出结构版本不在主要结果正文中展示，内部协议及历史记录继续保留。 |
