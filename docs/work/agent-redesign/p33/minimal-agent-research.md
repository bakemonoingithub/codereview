# P33 极简嵌入式 Agent 调研与实施参考

调研日期：2026-10-22（Asia/Taipei）。适用工作树：`agent/`，分支：`refactor/agent`。

本文记录官方工程实践、框架能力及对本项目的取舍建议，供 P33.1 设计和后续实施读取。负责人要求将调研结果落盘；落盘不表示新增建议已经逐项批准，也不启动 P33 实施。已确认业务以[业务契约第 4 节及 D-89](../business-contract.md#4-agent-分析的业务契约)为准，实施顺序以 [ROADMAP 第 7 节](../../../ROADMAP.md#7-p33-agent-专属设计html-原型实现及验收)为准。

## 1. 调研结论及适用边界

对于嵌入已有业务系统、只读调查代码、一次任务结束后固定保存结果的场景，单个模型、少量固定工具和受控执行循环可以构成首版 Agent。无需先建设独立规划器、反思器、多 Agent 编排或长期记忆。

上述结论来自下列官方资料呈现的共同实现模式，不是行业普及率统计。框架支持某项能力不表示本项目需要采用；外部资料中的默认值和代码示例也不是 P33 的参数基线。框架文档持续更新，实际引入依赖时须核对选定版本，不能把当前在线文档的接口直接当作项目可用接口。

本项目的固定 SHA、多提交比较关系、原始位置、材料完整性和报告冻结来自已确认业务，不能因为追求极简而省略。可以简化的是 Agent 内部的组织和扩展机制。

## 2. 官方资料与可借鉴事实

| 来源 | 调研取得的事实 | 对本项目的启示 |
| --- | --- | --- |
| [Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents) | 建议从简单方案开始，效果证明需要时再增加复杂度；框架抽象可能遮住真实提示词与响应 | 先实现可观察的小循环，保留实际调用阅读能力，不以框架层次多少判断完成度 |
| [Spring AI：Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html) | 默认工具循环由程序执行模型请求的工具、回传材料，直到模型响应不再包含工具调用 | 多轮工具循环本身足以构成基础能力，独立规划阶段不是必需步骤 |
| [LangChain4j：Tools](https://docs.langchain4j.dev/tutorials/tools/) | 提供低层工具请求及返回消息接口；同步 AI Service 默认顺序执行同一响应中的多个工具请求 | 当前任务内串行执行有成熟参考；即使使用库，也可保留业务对循环的控制 |
| [Pydantic AI：Output functions](https://pydantic.dev/docs/ai/core-concepts/output/#output-functions) | 输出函数接受模型提交的参数，经过校验后结束运行，结果不再发回模型 | 显式「提交结果」有成熟参考，可直接校验并保存，无需额外确认或总结调用 |
| [Pydantic AI：Usage Limits](https://pydantic.dev/docs/ai/core-concepts/agent/#usage-limits) | 分开限制模型轮次、工具调用及 token 等；其请求轮次计数不等于所有传输尝试次数 | 框架内置上限不能直接代替本项目预算，尤其要核对传输重试的口径 |
| [Anthropic：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) | 强调清晰的工具职责、说明、有意义的返回，以及分页、范围选择和过滤 | 优先改善工具的可用性及返回内容，减少依靠额外 Agent 阶段补救的需要 |

显式「提交结果」不是所有框架的默认结束方式。Spring AI 的默认循环可以在无工具调用响应时结束，Pydantic AI 则提供输出函数等方式。本项目选择显式提交，依据是结果固定保存、材料不足说明及代码引用的业务需要；具体规则已经按 D-89 记录在契约，本文不另行定义完成状态。

## 3. 首版能力取舍

以下表格是调研建议；已确认边界继续以业务契约为准。

| 能力 | 建议处理 | 理由 |
| --- | --- | --- |
| 单个 Agent 多轮调用工具 | 首版核心 | 调查方向需要随中间材料调整 |
| 目录、文件定位、内容搜索、读取、diff | 固定注册五类只读工具 | 已覆盖当前代码调查方向，无需先建设动态工具平台 |
| 单任务内的消息历史 | 保留完整会话历史 | 支持连续调查；与跨任务长期记忆是不同能力 |
| 参数校验、权限及版本检查 | 保留 | 模型选择工具，程序控制实际访问 |
| 调用、时间、额度及上下文限制，取消 | 复用并补齐公共控制 | 简单循环仍需要确定的结束边界 |
| 工具材料、实际调用、固定结果和证据阅读 | 保留 | 支持用户核对与既有报告流程 |
| 独立规划器、反思器、评审 Agent | 首版后置 | 尚无真实失败证据证明必须增加这些阶段 |
| 长期记忆、跨任务自动学习 | 首版后置 | 一次任务制不依赖此能力 |
| 压缩、普通中断恢复、执行中追问、仓库写入 | 按契约不做 | 不因框架提供能力扩大既定首版范围 |
| 动态 Skill、MCP 平台、工具市场 | 当前不引入 | 少量内部工具可直接注册；统一工具管理不等于建设扩展平台 |

## 4. 对 P33 实现方式的建议

### 4.1 复用公共调用，新增薄的执行循环

2026-10-22 只读核对时，项目已具备公共模型调用、请求快照、任务期限与取消等能力。`backend/pom.xml` 使用 Spring Boot 3.3.5、Java 17，未声明 Spring AI 或 LangChain4j 依赖。`PromptMessage` 当时只支持 `system/user`，`ModelInvocationService` 主要发送角色与正文并读取响应正文；工具定义、工具调用消息及返回仍需适配。这些是调研时的工程现状，不代表后续实施时文件内容不变。

建议优先扩展统一组装与公共调用，增加 Agent 执行器及固定工具注册表，避免为 P33 整体迁入一套框架后再重复处理任务、存储和预算。实施前重新核对当前代码，不能绕开公共入口自行建立第二套模型调用。

这是工程建议，不是禁止使用依赖。若真实模型协议适配成本明显过高，可比较框架模块带来的收益，但需同时核对依赖兼容、每次请求快照、内部重试、消息历史、取消和预算口径；不能仅因框架能自动跑循环就认为业务边界已经满足。

### 4.2 优先改善工具返回

- 搜索返回路径、原始行号及少量上下文，并说明有无更多结果，减少重复定位。
- 读取支持行范围，明确实际返回范围、完整性及后续读取方式。
- 无匹配、部分返回和执行失败分别表达；错误在适用时提供缩小目录、调整参数等可行下一步。
- 仓库身份和允许访问的版本由程序限定，减少模型需要生成的参数；多提交仍关联各自固定比较关系。
- 单次输出可分页或限量；已经进入会话的材料不通过丢弃或摘要延长任务，继续遵守契约的容量终止规则。
- 保留统一工具接口，但首版无需扩展为插件发现、远程协议或动态工具加载系统。

### 4.3 保持单一任务控制与轻量界面

建议使用一个 Agent 任务执行器；沿用公共任务状态，结合停止原因和回答充分程度表达结果，避免复制一整套任务控制。是否需要新增状态、字段和表，在 P33.1 结合当前数据结构确定。

详情页围绕结果、当前动作、已查范围和按需展开的调用／材料组织，不建设流程编排界面。过程展示来自可观察的请求和工具事件，不要求生成或展示模型内部思维过程，也不虚构完成百分比。

### 4.4 明确所有计量口径

P33.1 应分别说明模型轮次、实际请求尝试、工具执行次数、累计消耗及单次上下文占用，避免使用同一个「次数」字段表达不同含义。所有重试纳入契约要求的相应预算；若采用库，核查其传输重试是否绕过业务计量。

执行循环达到限制时终止，保留已有内容与原因；不增加总结 Agent 或越过硬限制的收尾调用。具体预算数值由设计与实测确定，不能复制官方示例的数字。

## 5. 实施顺序与真实任务验证

P33.1 设计及 HTML 原型完成后统一确认，随后按 ROADMAP 连续实施 P33.2–P33.6；中间的小型工程验证不另设常规负责人确认点。若出现改变已确认业务行为的问题，再按工作区约定处理。

首个实现验证使用小任务完成「模型请求工具 → 系统返回材料 → 继续调查 → 显式提交结果 → 用户打开证据」。随后扩展到跨文件搜索、多提交和失败边界；最小流程成功不能替代 P33.6 的真实联合验收。

建议准备以下真实任务及异常样本，最终对象和通过条件在 P33.1 确定：

| 场景 | 重点核对 |
| --- | --- |
| 单文件或指定方法的问题 | 能否按要求定位和读取，引用是否准确 |
| 跨文件业务链解释 | 是否找到入口及关联实现，能否基于中间发现继续调查 |
| 多个非连续提交综合分析 | 是否逐项使用固定比较关系，避免用最终版本混替证据 |
| 材料不足 | 是否明确未解决事项，避免把未取得材料解释为不存在问题 |
| 无匹配、截断、超时或读取失败 | 是否区分完整性与错误，能够在适用时调整调查方式 |
| 取消、容量或预算终止 | 是否及时结束、拒绝迟到发布，保留实际消耗与停止原因 |
| 专项与 Agent 混合报告 | 是否保持冻结来源、引用、下载及代码阅读一致 |

同时记录回答质量、引用正确性、实际请求和工具次数、耗时、消耗及重复搜索。只有出现可重复的实际问题，再考虑增加能力：例如重复定位先调整工具说明和返回；过量读取先调整过滤及范围；协议失败先核对模型能力；不能仅因任务失败就直接增加规划器或多 Agent。

## 6. P33.1 仍需明确的事项

- 实际使用模型的工具协议、工具调用标识及多轮消息要求，是否需要兼容方式。
- 工具与最终提交的字段、引用结构，以及同一响应出现普通工具和结果提交时的处理。
- 材料不足结果的冻结和展示衔接；选材资格已在后续按 D-90 确认，实施以契约及当前设计为准。
- 调用、工具、重试、时间、额度和容量的具体数值与检查位置。
- 搜索限制、缓存、镜像同步和目标环境的实际耗时。
- HTML 原型及正式页面的展示细节，真实验收对象与通过条件。
