# P29 专项执行与结果协议

状态：P29 已批准设计基线（2026-10-20，契约 D-88）。依据[契约](../business-contract.md)第 3 节、B-02 至 B-07、N-04 至 N-09。字段及算法进入 P30–P31 实施，候选数值仍须在 P30.8、P31.9 校准，真实使用由 P32.6 验收；不能视为目标仓库性能已验证。

## 1. 执行链路与统一组装

执行顺序拟为：校验并固定版本 → 保存输入与配置 → 按文件创建目标 → 读取目标及有限声明 → 建立整文件单元 → 统一组装并计量 → 调用及协议校验 → 程序归并与发布 → 汇总文件状态。各文件独立提交结果，公共调度限制模型请求并发。

`PromptAssemblyService.assemble(PromptInput)` 是专项、报告以及后续 Agent 的唯一消息组装入口。`PromptInput` 包含 purpose、协议版本、内置指令、可选策略、当前文件说明、版本化材料和本次格式重试诊断；调用侧不得自行拼接附加提示词。模型协议适配负责把有序消息和输出参数序列化；计量以适配后的完整请求为对象。入网前保存最终请求 body、消息、参数、adapter 版本、估算方法及长度；正文保存失败则不发请求。

消息顺序草案：system 为任务边界、优先级及输出协议；user 依次为策略、文件说明、范围与版本、目标内容、辅助声明及缺失说明。仓库代码、注释和辅助文档均放在带来源及长度边界的数据段内，明确不作为指令。格式重试追加实际错误和返回内容的有界引用，仍由组装入口生成并计入容量；不增加结论核验要求。

| 类型 | 默认指令的职责 |
| --- | --- |
| 问题／文件内容 | 根据目标代码和有限契约发现可说明原因与建议的问题；未知依赖行为列为边界，不凭印象断言 |
| 问题／提交差异 | 检查此次变更引入或违反选定规则的问题，关联修改前后位置与变更原因；历史问题不自动归入本次 |
| 设计模式 | 识别以当前目标文件为中心的模式候选、角色及代码依据；不宣称模块完整实现或所有候选均适用 |
| 耦合度 | 根据已计算的文件级依赖事实解释关系和风险，不让模型猜测缺失的指标或生成全仓指标 |

内置默认指令与协议优先于文件说明，文件说明优先于策略；无冲突要求共同生效。具体指令文本与 schema 在实施中版本化，原型的演示提示词不作为完整生产模板。

## 2. 结果协议草案

模型输出与服务端结果封套分开。服务端填写 `id/taskId/targetId/kind/schemaVersion/versions/completeness/materialGaps/sourceCallIds` 等可信元数据，模型不能指定稳定 ID 或执行状态。JSON 拒绝未知字段、错误类型、缺失必填和越界位置；结构检查不评价结论真伪。

### 2.1 共用位置

模型引用位置 `{materialId,startLine,endLine}`，正整数且在实际发送材料的原始行范围内；服务端据 materialId 补齐 repo、sha、path 和 `side=FILE/BEFORE/AFTER`。目标位置至少一个，辅助证据另列，不允许把辅助文件当作新问题目标。差异中的删除问题允许 BEFORE 位置，必须给出与本次变更的关联；新增文件只用 AFTER，删除文件只用 BEFORE。不把未验证位置自动改到相邻行。

### 2.2 问题审查

```json
{
  "summary": "订单写入与扣款之间缺少幂等约束。",
  "issues": [{
    "category": "CORRECTNESS",
    "severity": "HIGH",
    "title": "重试可能重复扣款",
    "locations": [{"materialId": "target-after", "startLine": 42, "endLine": 47}],
    "reason": "说明可由当前代码和契约支持的触发条件及影响。",
    "suggestion": "说明可执行的修改方向。",
    "evidence": [],
    "changeRelation": "新增重试使同一支付请求可以再次发送。"
  }],
  "limitations": []
}
```

category 候选为 `CORRECTNESS/SECURITY/RELIABILITY/PERFORMANCE/MAINTAINABILITY/RULE`；severity 为 `HIGH/MEDIUM/LOW`，只用于排序，不作自动真伪判断。summary、issues、limitations 必填，issues 可为空。changeRelation 在 DIFF 必填非空，在 FILES 为 null；evidence 为辅助引用列表。RULE 问题须在 reason 中指出选用规则。无证据支持的问题不为填满数组而生成。

### 2.3 设计模式

```json
{
  "summary": "目标文件承担策略接口角色。",
  "patterns": [{
    "name": "Strategy",
    "family": "BEHAVIORAL",
    "role": "策略接口",
    "explanation": "说明可见结构及其与模式的对应关系。",
    "evidence": [{"materialId": "target", "startLine": 8, "endLine": 16}]
  }],
  "limitations": ["仅分析目标文件与有限声明，未调查完整调用方。"]
}
```

family 候选为 `CREATIONAL/STRUCTURAL/BEHAVIORAL/OTHER`，name 为非空文本而非强制封闭模式清单；无需硬套经典模式，OTHER 必须有解释。patterns 可为空，每个候选至少包含一处目标依据。只对整个文件结果反馈，不对候选构造问题 ID。

### 2.4 耦合度

文件指标先由程序根据 Java AST 计算，再作为只读事实交给模型。以目标文件内声明的类型为中心，边来自父类型、字段、方法参数／返回、显式泛型类型与 `new` 类型引用；导入语句本身不算使用，注释、字符串、局部隐式类型和运行时反射不算已解析边。去掉目标文件内部类型和 Java 基础类型，自依赖不计数。泛型擦除后用规范化类型名去重；无法可靠解析则保留 unresolved，不把同名类型合并为确定身份。

`resolvedOutgoingCount` 为可靠定位到仓库内其他文件的不同类型数，`unresolvedTypeCount` 为规范化后未可靠定位的引用类型数。`declarationRelationCounts` 按继承、字段和签名等关系计数并去重，不能相加当作唯一类型总数。展示名明确为「仓库内已解析出向依赖」，不沿用类级完整 CBO 的名称或暗示覆盖全仓入向依赖。不提供未全仓计算的 fan-in、instability 或模块得分。

```json
{
  "summary": "目标文件集中依赖订单仓储与支付接口。",
  "observations": [{
    "title": "支付契约影响订单处理",
    "explanation": "解释输入依赖图中可定位关系的影响。",
    "dependencyIds": ["dep-1"],
    "evidence": [{"materialId": "target", "startLine": 12, "endLine": 18}],
    "suggestion": "如有必要，给出局部改进建议。"
  }],
  "limitations": []
}
```

模型只输出解释，指标、边及 dependencyId 由服务端封套携带并校验引用。目标 AST 解析失败导致指标无法生成时，该专项文件失败；不能返回零依赖。部分类型 unresolved 时可生成有边界的结果，指标同时显示 coverage 与缺失数量，不能宣称关系完整。非 Java 输入的耦合分析返回 `UNSUPPORTED_LANGUAGE`；问题及模式专项可直接分析受支持文本，增强不可用时说明限制。扩展其他语言解析器另行安排。

## 3. 材料定位及继承查找

1. 对固定 SHA 的路径清单建立仓库内 Java 源文件候选表；按限定名对应路径、显式 import、同包、嵌套类型及有限通配 import 依次定位。
2. 读取候选并核对 package 和实际类型声明；只有唯一可靠匹配才建立确定关系。名称相同或多个源码根重复声明时保留 AMBIGUOUS，不能按列表第一个取值。
3. 目标中 extends/implements 分支采用广度优先队列；访问键为 `(repo,sha,qualifiedName,path)`。每个祖先的父类和接口分支继续入队，循环去重，逐次检查深度、文件数及字节量。
4. 直接使用的请求、返回、字段类型只取必要字段和声明，不递归展开对象图。继承祖先提取类型、必要成员签名、注释及来源行号，不默认读出全部实现给模型。
5. 材料排序为目标 → 明确父类型契约 → 直接接口与请求／返回声明 → 其他允许的必要声明。同一版本已包含的目标声明不重复加入。
6. 每条记录标记 `RESOLVED/AMBIGUOUS/PARSE_FAILED/NOT_AVAILABLE/LIMIT_REACHED`，并区分已读取和实际发送。某分支缺失只停止该分支，其他分支可继续；未知不能作为不存在。

无 JavaSymbolSolver、完整 classpath 或编译器级重载绑定。方法名匹配只表示候选成员，不表示精确覆写或运行时实现；静态 import、泛型边界及复杂嵌套情况不能可靠定位时明确缺口。第三方类型归为外部资料不可得，不自动下载依赖、源码包或文档。

读取接口返回文本／二进制、编码、原始字节数、行数和完整性。目标读取失败、非法编码或目标被截断则该文件失败，不对半份文件输出完整成功。辅助材料失败可继续，但保留诊断。缓存按 `(project,repositoryIdentity,sha,path,range)` 隔离；只缓存确定版本，不缓存分支名作为内容身份。权限变化撤销相关缓存访问，缺失缓存不能把暂态 HTTP 失败固化为文件不存在。

## 4. 容量与智能拆分

未开启智能拆分：保留完整文件或完整差异目标，不精简目标；本地计量提供诊断，实际请求在模型硬参数合法范围内整份提交。模型端上下文超限直接以 `CONTEXT_LIMIT` 失败，不偷偷拆分或删去用户规则。无法发送完整目标的系统读取上限错误与模型容量错误分开说明。

开启后：先尝试完整目标和有限声明；若完整请求超限，移除低优先级可选辅助材料并重新组装；仍超限才按顶层类型及成员的连续原始行区间形成单元。覆盖清单必须包含 package/import、字段、初始化块、注释及类型外区域，不能只覆盖方法。单方法过大时优先 AST 语句边界，解析不可用时按行区间有限细分并标明非语义边界；不截断单行冒充完整代码。每个单元保留类型头、相关字段和必要签名，背景重复不算新增目标覆盖。

每个新单元以最终请求重新计量，输出预算和余量始终保留。若不可拆的单行或规则与协议自身已超过容量，返回 `UNSPLITTABLE`。模型端确定上下文超限时，停止旧 generation 未开始调用，已发请求只作诊断，不用于新结果；有限次数重新规划，防止旧代迟到内容混入。并发单元各自重试不扩展到开放调查。

优先使用声明与模型匹配、实现可核实的 tokenizer；缺少时拟用 UTF-8 字节上界加请求封装保守余量，并明确 `ESTIMATED`，不能声称精确。未经适配测试不从模型名猜测 tokenizer。`inputEstimate + outputReserve + safetyReserve <= contextWindow` 才是估算可容纳；模型仍可报超限，按同一授权规则处理。

### 4.1 候选运行参数

以下仅为本地验证起点，不是确认的生产默认值；不放进发起表单。实际目标仓库约 2,894 文件／170 MB 的规模来自 D-49，本轮未对该仓库采样或计时。

| 参数 | 候选值／规则 | 验证及失效处理 |
| --- | --- | --- |
| 全局模型并发／单任务占用 | 4／最多 2 | 两批任务和慢调用验证公平性、取消与排队；按服务承载调整 |
| 继承深度／辅助文件数 | 6／12 个不同文件 | 深链、菱形、循环和同名类型样本；命中后显示 LIMIT_REACHED |
| 辅助读取／辅助发送量 | 256 KiB／最多可用输入 20% | 多字节源码及大声明；目标优先，超出不继续扩展 |
| 目标读取上限 | 4 MiB 文本／文件 | 超大目标明确失败；不能静默截断；需根据目标仓库复核 |
| 输出预算 | 4,096 tokens 且不超过模型最大输出 | 确认模型输出限制及完整结果大小，截断当协议失败 |
| 安全余量 | `max(1024, ceil(contextWindow×0.10))` | 精确 tokenizer 与估算对照；无法保留输入时配置校验失败 |
| 容量重规划／总单元数 | 最多 2 次／每文件最多 32 单元 | 模型反复报超限和超大方法；耗尽失败 |
| 协议重试 | 每单元最多额外 2 次 | 契约已确认，不作为可调候选放开 |
| 暂态传输重试 | 每调用步骤最多额外 1 次 | 仅可重试 429、明确暂态 5xx 和连接失败；总请求硬上限仍约束 |
| 单任务请求硬上限／期限 | 200 次／30 分钟 | 所有尝试均计入；配额不足停止并显示原因；不继承旧表单预算 |
| 连接／单次响应超时 | 10 秒／180 秒且不超过任务剩余期限 | 本地慢响应及取消；超时不伪装模型未执行 |
| 材料缓存 | 128 MiB 有界内容缓存；暂态失败不缓存 | 多仓库版本隔离、回收与权限验证；磁盘镜像单独限额 |

HTTP 错误先分类：鉴权、配置、不可读输入不重试；限流遵循有上限的 Retry-After，等待计入任务期限且不占模型执行许可；上下文超限只认适配器结构化错误码，未知 400 不凭模糊文本拆分。返回正文截断／finish_reason 为长度限制视作输出不完整，走格式错误路径。协议重试、传输重试和容量规划分别记原因，但每次实际请求均占用同一总请求额度，不能多层重试绕过上限。

## 5. 汇总、去重及发布

每个结果关联 callId、unitId 和 generation。全部当前代单元成功后才发布完整文件结果。问题去重键候选为 `(repo,sha,path,side,startLine,endLine,category,normalizedTitle)`，只归并确定一致的条目并保留全部来源单元；同位置不同原因不强行合并。模式条目以规范化名称、角色及相同证据位置去重；耦合边按源类型、目标类型及关系去重，解释条目保留原文，不用额外 LLM 合并。

批次汇总只计算文件状态和问题数量，不生成跨文件联合结论。片段未完成时只展示已取得内容和缺失区间，标签为「文件未完成」；结果选材和统计排除该文件，已成功的其他文件不受影响。原始行号和前后侧贯穿读取、单元、结果、代码阅读及报告引用。

## 6. 验证落点

P30 验证快照、版本、配额原子预留、取消终态和请求落盘；P31 验证三类协议、源位置、整文件与拆分授权、覆盖及部分失败；P32 验证稳定反馈对象、统计空分母、输入冻结及报告引用。实际模型结果质量和目标仓库资源阈值分别记录，不能以本原型或来源测试数量替代。具体样本及状态见[验收清单](acceptance.md)。
