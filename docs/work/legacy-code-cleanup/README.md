## 1. 目标、状态与依据

## 2. 清理范围与保留边界

### 2.1 后端候选范围

候选位于 `backend/src/main/java/com/codereview/` 下的旧 `controller`、`service`、`analyzer`、`chunk`、`diff`、`material`、`review`、`dto`、`entity`、`mapper`、`llm`，以及部分 `common`、`config`、`probe`、`gateway` 文件。这里列出的是调查目录，不是整目录删除指令。

现行启动类只扫描 `com.codereview.agent` 和 `com.codereview.git`，并显式导入公共配置；「不在默认扫描范围」只是判定依据之一。还必须检查 Java 静态引用、Spring 注入、手工构造、反射与配置类名、脚本和独立实验入口。

现行 `com.codereview.agent.specialist.material` 是当前专项材料实现，不属于旧 `com.codereview.material` 的清理范围。现行任务执行、模型调用、提示词、Schema、额度、重试和容量算法均保持。

### 2.2 前端候选范围与旧地址去向

- 旧 `ProjectDetail.vue` 仍由 `/projects/:id` 路由加载，应解除该路由与旧页面的关联。
- 默认将 `/projects/:id` 导向现有 `/projects`，避免旧收藏地址继续加载旧实现或出现意外空白。现有代码浏览页没有已核实的项目查询参数接入，不在本次擅自增加携带旧 ID 的跳转协议。
- 清点旧页面关联的 `ReportPanel`、旧审查结果组件、文件查看组件、旧 API 模块、工具函数、样式及测试，只删除不被现行入口复用的部分。
- `/strategies` 的现有停用提示页默认保留：它不提供旧策略功能，用于解释旧地址去向，不因名称带有「策略」就删除。
- 不新增产品页面或改变现行布局。若实施时发现确需新的页面结构，按工作区规则先形成独立 HTML 原型再进入框架实现；单纯使用现有页面进行重定向，不扩展为页面重设计。

| ID | 工作项 | status | depends_on | 主要产物与完成条件 |

| LGC-01 | 固定清单、保留项与改造前基准 | done | - | 逐文件处置清单、当前有效接口清单、测试归属和可比较的改造前检查结果 |
| LGC-02 | 关闭前端残留入口并清理独占页面依赖 | todo | LGC-01 | 旧项目地址转到现有项目列表，现行入口不再依赖旧 API，相关前端检查通过 |

顺序为 `LGC-01 → LGC-02 → LGC-03 → LGC-04`。前端与后端分成独立可检查批次，避免一个批次同时改变入口、删除实现并失去问题定位依据。每步内部的清单、修改和必要检查合并处理，不再拆成大量小里程碑。

### 3.1 LGC-01：固定清单、保留项与改造前基准

1. 核对 `dev`、完整提交、已有工作区修改和正在运行的开发环境；使用隔离副本与独立构建输出，避免清理或覆盖原文件。共享工作树中的用户修改和构建生成内容单独记录，不混入清理补丁。
2. 形成 `inventory.md`。每个生产、测试、配置和资源文件至少记录路径、处置方式（删除／保留／必要调整）、依据、关联消费者和验证项目。候选目录不能替代逐文件清单；原位保留项必须写出仍服务的消费者或保留理由。
3. 同时检查静态引用与运行装配。重点包含 `List<Analyzer>` 等注入实现、显式 `@Import`、入口脚本、字符串类名和迁移工具；避免仅按 import 图判定无用。
4. 从前端路由、入口文件、动态 import 和组件引用追踪旧页面依赖，区分执行时调用旧 API、仅引用旧类型和完全无引用。保留现行 `api/v2.ts` 消费者；不能把文件名相似当作复用证据。
5. 核对现行自定义 HTTP 方法与路径、DTO 关键契约和启动范围，形成可比较的接口清单。40 个旧接口应继续不注册；不为了建立基准启动业务服务。
6. 记录测试类到生产代码和资源的归属，区分旧专属、共用、当前有效和历史迁移保留测试。测试归属依靠断言与依赖，不只按包名决定。
7. 在未改生产实现的隔离副本执行后端及前端基准检查，保留命令、环境、通过／失败／跳过项目。已知问题必须在 before 复现后单独登记；不能删除失败测试或刷新期望来制造基准通过。

完成条件：每个拟删除文件有依据，每个受影响的现行消费者有去向，基准及已知失败可重现。不能以「前期已盘点约 96 份」直接跳过此步。

### 3.2 LGC-02：关闭前端残留入口并清理独占页面依赖

1. 将 `/projects/:id` 从旧页面改为重定向到 `/projects`；核对旧地址直达、浏览器刷新与返回行为。不把旧数字项目 ID 自动解释为新项目 ID。
2. 按清单删除不再被当前入口使用的旧项目详情、旧审查／报告／标记组件及专属 API 模块。公共组件和工具函数有现行消费者时保留；仍需使用的类型定义应迁入合适的当前文件，而不是为了一个类型继续保留整个旧 API 客户端。
3. 删除被移除功能的专属测试，保留或调整当前行为的有效断言。为旧地址不再加载旧页面、重定向目标正确补充必要路由覆盖；不为纯删文件机械新增测试。
4. 检查 `components.d.ts` 等生成声明，保留 LGC-01 记录的已有修改，只处理本次删除直接造成的失效引用。通过隔离前后对比区分工具自动变更与用户修改。
5. 执行相关前端测试、类型检查和构建。核对当前代码浏览、项目编辑、任务详情、材料查看和报告来源阅读不再借用旧接口。

完成条件：当前路由和构建入口不再加载旧业务界面，旧 API 的执行引用已经消除，剩余引用均有明确保留理由。默认不做正式页面视觉验收；若实际新增布局或交互，则记录其额外验收要求，不能用构建成功代替。

### 3.3 LGC-03：清理后端旧实现与专属测试，处理外围引用

1. 先删除 7 个旧控制器，再按依赖清单清理旧服务、执行器、分析器、材料实现、DTO、实体和 Mapper；将相关旧测试与实现放在同一可编译批次中处理。不按父目录一键递归删除。
2. 每批检查编译与直接相关测试，清除失效 import、手工构造和配置引用。遇到现行依赖时保留或缩小删除范围，不通过复制旧逻辑进 `agent/` 绕过检查。
3. 清理无独立用途的旧配置、用户辅助对象和探针。对保留探针列出使用条件及依赖；历史迁移 SQL、对应契约测试和独立迁移工具按第 2.3 节保留。
4. 检查现行注释中的过时描述，例如旧异常处理仍参与运行、旧数据源自动装配仍启用等。只修正对当前机制的错误说明，不追改全部历史文件。
5. 核对 Maven／前端依赖的剩余消费者。确无生产、测试、脚本或工具用途时，才删除直接失去用途的依赖，并同步需要变更的锁文件。数据库、Flyway、MyBatis、JavaParser 和 Jackson 等依赖不能因为旧实现曾使用它们而直接移除；不随本轮升级版本或更换框架。
6. 涉及当前规则维护关联入口的必要调整时，按 [BRC 维护索引](../backend-rule-consolidation/maintenance-map.md)核对说明和注释。保持提示词资源、请求／工具基线、Schema 及现行业务校验原意。

完成条件：清单中的旧独占生产代码及专属测试已处理，没有从现行实现指向被删除文件的有效引用。剩余旧名文件、迁移资料、测试或探针均有明确用途；不要求仓库内所有「旧」「legacy」字符串归零。

### 3.4 LGC-04：全量验证、交付记录与状态关闭

1. 对最终候选重新核对删除清单、保留清单、接口方法／路径及当前入口引用。现行接口清单保持，旧接口仍未注册；框架路由和历史文档文本不作为误报删除。
2. 完成后端全量测试和打包、前端全量测试、类型检查与构建。失败应定位为本次回归或已有问题；本次引入的问题修复并复验，不能通过新增跳过规则或关闭质量检查处理。
3. 对比测试清单，记录每个消失的测试类、用例数和原有责任，区分随功能删除、迁移到保留测试及继续保留。尤其保留迁移契约与共用能力测试；不能把少跑 225 个用例作为验收标准。
4. 核对现行提示词资源、固定请求与工具基线未被重录；核对打包资源与源码一致、最终产物不再包含计划删除的生产类。仍保留的历史 SQL 和独立工具不记为清理失败。
5. 用现有替身、路由及装配测试验证必要行为，不增加测试专用业务分支。使用隔离装配核对 `/api/v2` 入口及旧控制器未注册；不以真实仓库、数据库或模型调用替代代码清理验证。
6. 编写 `delivery.md`，记录最终提交或候选补丁与哈希清单、实际删除和保留范围、接口差异、测试变动、全部检查及未验证边界。当前文档的导航应更新到有效入口；历史文档中的旧源码路径使用「删除前提交＋原路径」定位说明，不批量改写证据。
7. 同步 STATE、ROADMAP 和本计划的状态。只有要求的检查与问题处理完成后，才将 LGC-04 标为 `done`；未执行的真实环境或视觉验收单独说明，其他工作包的待办保持原状态。

完成条件：最终候选和验证对象一致；有效功能保护项通过；删除与保留依据可审阅；没有未说明的新增失败或测试排除。

### 4.2 执行原则

- LGC-01 记录改造前基准，LGC-02／03 各做相关检查，LGC-04 只对最终候选执行必要的完整验证。检查通过后，只有新修改、失败或未决风险才触发重跑。
- 后端使用 Maven Wrapper 和独立 `backend.buildDirectory`；前端在隔离副本使用仓库现有 pnpm 脚本，不在用户正在运行的前端目录生成或清理构建结果。
- 后端基准与候选均使用不含真实调用凭据的测试子进程；隔离 `DEEPSEEK_API_KEY`、远端仓库探针变量以及可能注入参数的环境项，传空 `deepseek.api-key`，不启用 `probe.root` 或 `agent.live.cancel`。不要重复使用历史上导致严格配置绑定失败的 `-Dagent.live.cancel=false`。
- 记录所有跳过项及原因，不以单纯跳过来证明未访问外部服务。检查脚本、测试装配和隐式配置读取，避免继承现有服务配置触发真实访问。
- 前端类型检查若存在基准问题，候选至少做到无新增问题，并明确报告原问题；本次引入的类型错误必须修复。不能临时禁用类型检查或扩大排除范围来通过。
- 源码、模板、接口与页面均依靠直接证据核对；全量测试通过不等于真实模型审查质量或生产部署验收通过。

### 4.3 故障处理与可逆性

按 LGC-02／03 保留可独立审阅的改动批次，允许使用未提交补丁及候选哈希，不自动提交、推送或发布。发现现行功能依赖误删文件时，先恢复本批被误删的源码并修正清单，再运行相关检查；不改弱业务断言，也不恢复全部旧业务入口来绕过问题。

回退仅限本次源码、配置声明及依赖文件的变更，不回退数据库、不清理工作目录、不覆盖原有未提交修改。需要重跑验证时使用隔离候选，不停掉当前业务服务或切换用户工作分支。
