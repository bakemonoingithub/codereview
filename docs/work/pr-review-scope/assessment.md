# PR 审查范围改造评估

日期：2026-11-06。性质：需求与技术影响评估，尚非实施方案或业务契约变更。评估对象为在「专项审查—查找问题」及「Agent 分析」发起页增加手工选择待合并 PR 的范围模式，覆盖当前内网 Gitea 1.16.1 仓库和开发所用的 GitHub 验证仓库。PR 自动触发、结果回写代码托管平台、合并拦截及 Jenkins 集成另行论证。当前一切既有功能以内网正常运行为前提；本轮未修改业务代码、数据库、GitHub／Gitea 集成接口或现有任务状态。

配套的[交互原型](prototype.html)借用了 P29 工作台的基础视觉，使用本地示例数据演示选择 PR、发起两类审查、阅读结果／代码证据／材料／实际调用；不连接实际仓库或业务接口。原型与当前 Vue 前端仍有布局差异，**正式实现以 `frontend/src` 的现有页面、组件和样式为准，不照搬原型页面结构**。视觉验收由负责人完成。

## 1. 结论与范围语义

建议将 PR 作为独立的审查来源，而不是将 PR 展开为一组「逐提交审查」。一次 PR 审查应固定目标仓库与 PR 编号、目标分支及其提交 `targetHead`、源分支及其提交 `sourceHead`、共同祖先 `mergeBase`，以 `mergeBase → sourceHead` 的**净变化**定义本次变更。PR 内有多少提交，不改变这一审查对象。结果只代表这些固定版本上的变更调查，不代表合并后代码已通过编译、测试或人工确认。

这里的 `targetHead` 是选择 PR 时目标分支的提交，不是项目配置的默认分支，也不是源分支第一条提交的父提交。目标分支移动、源分支推送或 PR 更换目标分支后，既有结果仍可回看，但对当前 PR 必须标记「版本已变化，需重新审查」。目标分支移动后，系统仅对受影响的PR进行提示，是否重审交由用户；系统至少要显示两侧版本和变化状态。

建议首版只接受已登记项目仓库中、目标分支可读、未关闭且有可解析共同祖先的 PR。跨仓库 PR、无共同祖先、目标仓库或源提交不可读时给出明确失败，不降级为单提交审查。这里的跨仓库包括来自 fork 的 PR；GitHub 与 Gitea 均须遵守相同的首版范围规则。

现有专项 `DIFF` 输入虽有 `baseSha`，实际材料读取仍由 `RepositoryReadService.diff(projectId, headSha, path)` 取所选提交的第一父提交。Agent 的 `COMMITS` 也是各提交与第一父提交逐项比较；`read_diff` 的清单与逐 hunk 读取同样依赖单提交详情。这些实现不能直接承载 PR 净差异。Gitea 适配已有基于 `merge-base` 的两端变更**路径**计算；GitHub 适配已有两端比较的变更**路径**获取。两者都没有供现行审查链路使用的完整 PR 比较材料。

### 2.1 Agent 详情

「审查输入」需显示 PR 编号、标题与链接、源／目标分支、`sourceHead`、`targetHead`、`mergeBase`、发起时净变化文件数、文本／二进制／无法读取计数及用户要求。不要把 `PR` 显示成 `COMMITS` 的逐提交列表；提交列表若提供，也只是辅助元数据。固定代码预览应依据被点击材料的 SHA 读取，而不能一律取当前 `observedSha` 或任务 `headSha`。

「审查结果」现有 Markdown 正文、完成程度和「代码证据」列表可复用。每条证据继续按材料 ID、路径、SHA、前／后侧及原始行号定位，页面增加 PR 版本摘要和覆盖边界提示。代码证据的 `BEFORE` 应对应 `mergeBase`，`AFTER` 对应 `sourceHead`；若调查目标分支当前内容，须单独标记 `targetHead`，不得把三种版本混为一个「修改前」。报告引用仍以已保存的材料为准。

「实际调用」记录列表与参数／返回阅读可复用。建议**不新增 `read_pr` 模型工具**：在任务创建时将 PR 解析为冻结的版本和一个 PR 比较关系，让既有 `read_diff`、`read_code`、搜索等工具在固定作用域内工作。但 `read_diff` 的内部实现必须改为按比较关系读取净差异；仅向模型提供新 `comparisonId` 不能解决当前第一父读取问题。工具返回需明确比较基线和完整性；仍不允许模型自行查询任意 PR 或移动中的分支。若后续需要模型读取 PR 讨论、审批、流水线状态，才另评估新工具及权限。

### 2.2 专项详情

结果协议仍以**一个文件一份结果**为主，问题标题、严重度、位置、辅助证据、人工反馈和统计口径无需改为「每提交一份」。左侧「目标文件」仍逐文件列出状态和问题数；PR 模式在列表上方增加 PR 及版本摘要，并显示「已选／可审查／全部变更」计数。文件名以 PR 净变化后的路径为主，重命名显示原路径，删除显示删除标记。不能让未选文件或二进制文件在列表缺席后被误读为已审查。

「输入与配置」的任务配置增加 PR 身份和固定三版本信息；当前文件的「代码材料」仍分目标与辅助材料。目标材料分别标明 `mergeBase` 的修改前、`sourceHead` 的修改后，保存路径、SHA、行号、完整性和实际发送情况。新增文件没有前侧、删除文件没有后侧；重命名保留两侧路径。现有代码阅读弹窗可复用，但不能通过单提交差异接口重新构造 PR 材料；优先读取任务已保存材料，扩展原文件时按材料固定 SHA 读取。

## 3. 后端影响

### 3.1 PR 来源、版本与材料获取

**需要新增 GitHub 与 Gitea 的 PR 只读集成接口，尚未授权实施。** 现有 `GitHostClient` 与 `/api/v2/projects/{projectId}` 仓库读取接口只提供分支、提交、路径、文件和单提交差异，没有 PR 列表或详情。选择 PR 模态框至少需要服务端分别增加：Gitea 1.16.1 的 `GET /repos/{owner}/{repo}/pulls` 与 `GET /repos/{owner}/{repo}/pulls/{index}`；GitHub 的 `GET /repos/{owner}/{repo}/pulls` 与 `GET /repos/{owner}/{repo}/pulls/{pull_number}`。本系统也需提供统一的 PR 列表、详情只读接口供前端使用，按现有仓库类型分派。建议的接入层按项目仓库列出／定位 PR，校验目标仓库、状态、权限及分支，读取源／目标固定 SHA，并构造冻结的 PR 比较关系。创建任务时服务端再次读取 PR 并核对用户确认的两侧 SHA；若已变化，返回类似现有 `SOURCE_MOVED` 的明确诊断，让用户刷新范围。任务创建之后不再跟随 PR 移动。上述新接口及其参数、权限和错误契约须在实施前单独提交负责人确认；本评估没有新增或调用这些接口。

材料层要从「单提交详情 → 第一父差异」扩展出「两个固定端点 → 共同祖先 → 净变化文件清单、前后文本和补丁」。建议在 `RepositoryReadService` 增加独立的固定比较读取能力，供专项材料准备、Agent `read_diff`、前端预览复用；现有单提交入口保留原语义。重命名、增删、模式变化、二进制、补丁缺失和清单截断须有统一状态，不把「没有 patch」直接等同于「二进制」。仓库镜像的 `changedPaths` 只有路径，不足以支撑状态、旧路径、逐 hunk 与完整性判断。

Gitea 1.16.1 源码可确认 PR 列表、单个 PR 及 PR `.diff`／`.patch` 路由；该版本路由表未见 `/pulls/{index}/files`。因此不能按新版 Gitea 文档假定存在逐文件 PR JSON 接口。**首选复用现有本地镜像并扩展其固定 SHA 比较能力**取得文件清单与材料，不默认增加 Gitea PR diff 调用；若镜像方案不能覆盖已确认样本，再单独提出 `GET /repos/{owner}/{repo}/pulls/{index}.diff` 的新增调用及影响供负责人决定。新 PR 能力在内网实例的权限、分页、跨仓库 PR 和规模限制需要验证；既有分支、提交和单提交差异能力无需因本评估重新验收。[Gitea 1.16.1 PR 路由源码](https://github.com/go-gitea/gitea/blob/v1.16.1/routers/api/v1/api.go)、[PR 读取与 diff 实现](https://github.com/go-gitea/gitea/blob/v1.16.1/routers/api/v1/repo/pull.go)。

GitHub 官方提供 PR 列表、详情及 `GET /repos/{owner}/{repo}/pulls/{pull_number}/files`；后者返回逐文件状态、路径和可选 patch，但最多返回 3000 个文件，不能将达到上限的清单视为完整。现有 `GitHubClient.changedFiles(base, head)` 仅从 compare 响应取路径；它不能代替完整 PR 文件状态及前后材料。GitHub 材料方案可优先评估 PR 文件接口与按固定 SHA 读取前后文本的组合，必要时评估本地镜像；选择前须核对净变化语义、分页／上限、重命名和补丁缺失。**调用 PR 文件接口也是新增 GitHub 集成接口**，须随方案明确提交负责人确认。[GitHub PR REST 文档](https://docs.github.com/en/rest/pulls/pulls)、[GitHub compare REST 文档](https://docs.github.com/en/rest/commits/commits#compare-two-commits)。

### 3.2 提示词与组装

提示词**需要改范围事实，不需要推倒统一组装架构**。专项的「范围与版本」需把来源写为 PR，写明 PR 编号、目标／源分支、`mergeBase` 和 `sourceHead`，明确任务是检查 PR 净变化引入的问题；目标材料仍逐文件，辅助材料仍只作证据。不能沿用「本次提交」或将 `mergeBase` 标为「第一父提交」的措辞。Agent 的范围段落需说明「一个 PR 整体比较关系」，明确 `BEFORE`／`AFTER` 版本、净变化与非目标背景材料；原 `COMMITS` 的「逐项比较、不合并成首尾净差异」规则不适用于 PR。工具使用和输出协议只有在新增状态、比较关系或引用类型确实变化时才改相应说明，不预先增加新的 Agent 执行循环。

现有 `PromptAssemblyService`、`SpecialistPromptStrategy`、`AgentPromptStrategy`、公共段落及模板体系可以保留。建议扩展类型化范围输入与 PR 专用措辞，再由原策略组装；不要把 PR 文案拼在 Controller 或执行器里。正式改动前须按本项目的提示词／工具三档维护要求，核对模板、Schema、检查器、维护索引及固定请求基线；本评估不批准改动现有提示词正文。

### 3.3 材料增强

专项的有限 Java 声明增强可继续按目标材料的 `sha + side` 解析：前侧在 `mergeBase` 查声明，后侧在 `sourceHead` 查声明，继续遵守文件数、字节数和深度上限。架构无需另建增强器，但要检查当前 `PreparedTarget`、`DeclarationResolver` 对 `baseSha`、重命名和删除文件的传递，保证不把目标分支最新代码当作任一侧的背景。PR 全局跨文件调查仍归 Agent；专项不因 PR 范围扩大而自动变成整个 PR 的联合分析。Agent 沿用只读工具按冻结版本调查，不启用额外的自动声明增强。

### 3.4 审查单元与大 PR

专项任务的容器是一个 PR 固定版本，调度和结果单元仍是**一个选定目标文件**；单文件过长时沿用当前「智能拆分文件」策略和片段结果汇总。一个文件在 PR 中被多个提交修改，也只按最终净变化审查一次。一个提交修改多个文件，则分入各文件单元；不能为每个「提交 × 文件」建重复单元。Agent 任务的审查单元是**整个 PR 的一次调查**，工具调用按文件、范围和比较关系逐步取证，结果只发布一次。

PR 中提交多，不必然造成材料大：相互抵消的提交可能没有净变化；相反，单个提交也可能产生大量净变化。主要压力来自净变化文件数、文本字节数、差异计算与镜像拉取、专项并发和模型调用量、Agent 轮次／工具／时间／上下文预算、数据库材料与调用记录、前端清单展示。发起前应给出可审查文件数和估算规模，按现有限额分层处理；超出清单完整性或系统硬限制时明确拒绝／终止，不静默取前 N 个文件后声称 PR 已审查。专项允许用户选择部分文件并在结果标明覆盖率；Agent 命中预算时保持现有部分／失败语义，不能发布完整结论。无需因为「某个提交大」另设逐提交分块，除非正式需求要求追踪每次提交的独立影响。

### 3.5 二进制及其他不可审查内容

纯二进制 PR：可以展示 PR 元数据和文件清单，但两条文本审查路线均不应给出「未发现问题」的成功结果。建议发起前显示「无可审查文本变更」，禁止创建专项／Agent 文本审查任务，并给出二进制文件数和路径；是否未来增加元数据级检查另立需求。二进制判定须依据实际文件内容或 Git 变更类型，不能只依据扩展名或 patch 为空。

文本与二进制混合：文本文件可审查；二进制文件在范围预览和结果覆盖边界中保留为「未审查」，不发送原始二进制给模型。专项的成功只针对已选且完成的文本文件；Agent 若形成结果，必须列明二进制缺口和未覆盖范围。无法读取、过大、子模块指针、Git LFS 指针、生成文件等不应一律归为二进制；分别记录可读性和分析边界。具体是否审查 LFS 的真实内容，需按内网仓库能力决定。

## 4. 其他受影响点

| 项目 | 影响与建议 |
| --- | --- |
| API、快照和数据库 | 两条创建接口、范围 DTO、任务 `inputSnapshot`、列表／详情读取、复制参数都需识别 `PR`。优先沿用 JSON 快照并评估是否需要可查询的 PR 关联字段；不能只存 PR 编号，必须持久化固定版本及比较关系。是否需要迁移由查询与索引需求决定。 |
| 证据与结果协议 | 尽量保留现有材料 ID、SHA、side、行号和结果 Schema。若引用需要区分 `mergeBase`、`targetHead`、`sourceHead`，先核对现有三值 side 是否足够；必要时扩展版本角色，不让同一个 `BEFORE` 含糊对应两种基线。 |
| 报告 | 报告候选、冻结来源、事实摘要和来源阅读要显示 PR 身份与版本；现有报告文案把 `baseSha` 称为「父」，PR 模式必须改为「共同祖先／比较基线」。只允许完整发布的文本审查结果进入候选，报告不能把未选文件或二进制算作已审查。 |
| 反馈与统计 | 问题级反馈、结果级反馈仍挂现有结果；统计可复用，但按 PR 展示时应分清「已发现问题数」与「覆盖文件数」，不把无文本结果记为零问题。 |
| 权限与数据隔离 | PR 可能来自另一仓库或受限分支；分别核对项目绑定仓库、GitHub／Gitea 凭据权限、跨仓库读取和 URL 校验。PR 标题、描述及代码均为不可信输入，不得覆盖内置提示词或扩大模型工具的版本作用域。 |
| 幂等、取消与过期 | 同一个 PR 的两侧 SHA 组成任务版本键；重复提交、页面重试和未来事件触发须避免重复任务。PR 更新不改写旧任务，取消和迟到结果仍按现有任务终态处理。 |
| 集成边界 | 手工选择 PR 不自动等于 GitHub／Gitea 回写或合并门禁。将来若接入 PR 评论、状态或 Webhook，需单独设计身份、重试、去重、版本失效和权限；负责人「必须看到结果」的业务约束也需要明确失败／不适用如何处置。 |

## 5. 实施前的关键决策（已决策）与验证

1. **先固定语义**：PR 范围是 `mergeBase → sourceHead` 的净变化；不需要同时分析与 `targetHead` 的集成冲突、目标分支变动后的强制重审。首版只展示差异及版本变化，不承诺合并后行为验证。
2. **先确认新增接口，再验证新能力**：负责人分别确认 GitHub、Gitea 的 PR 列表／详情调用及本系统对应只读接口后，在两种宿主上验证同仓库样本、源／目标 SHA、分页和权限；按选定材料方案验证固定比较、二进制、重命名、删除、目标分支推进和强推后的结果。GitHub PR 文件接口、跨仓库 PR、Gitea PR diff 调用如需纳入，分别列出接口与样本。已有功能的内网正常使用不作为待修复问题。
3. **确定覆盖规则**：专项是否默认全选可审查文本文件、用户可否只选一部分；Agent 对纯二进制和部分不可读 PR 如何终止；结果怎样向负责人显示「审查完成但覆盖不全」。
4. **按依赖实施**：先做冻结 PR 来源与完整净差异材料，再改专项与 Agent 的范围、提示词和工具，随后改两套界面、报告来源及版本过期提示。完成后用多提交净差异、目标分支独有提交、同文件反复修改、重命名／删除、超大与纯二进制 PR 做端到端验证。

本评估不改变现有 `STATE.md`、`ROADMAP.md` 或业务契约中的阶段状态；上述设计选择在实施工作包立项时确认。
