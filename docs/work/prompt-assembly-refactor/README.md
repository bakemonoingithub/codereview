# 提示词组装与工具描述重构计划

日期：2026-11-01。状态：PAR-01–PAR-03 已完成，PAR-04–05 未启动。负责人已授权完成基线、编写指南、原样抽取内置正文并提交；不包括职责收敛、数据库、服务或插件框架实施。

## 1. 目标与依据

将内置提示词正文与执行逻辑分离，明确统一组装入口、场景规则与工具描述的职责，保留后续插件能力接入空间。业务行为以[业务契约](../agent-redesign/business-contract.md)为准；后续能力方向参考[插件框架讨论](../plugin-framework/README.md)，不将其中候选 schema、接口名称或实施建议视为已定稿。

当前专项、Agent、报告、连通验证及工具协议验证已经复用 PromptAssemblyService 和 ModelInvocationService。主要问题是正文分布于 PromptAssemblyService、PromptPurpose、SpecialistProtocol、AgentToolSchema，AgentTaskWorker 仍直接生成部分纠正指令。当前已有用户提示词版本及实际请求快照，不重建公共调用体系。旧包中的执行器不因源码仍存在而自动纳入当前运行范围；实施前按应用扫描、依赖及调用点复核。

## 2. 重构范围与职责

| 内容 | 计划处理 | 保持边界 |
| --- | --- | --- |
| 内置正文 | 抽取为随应用发布的独立模板资源，以清单记录稳定标识、版本及变量约束 | 首轮原样抽取，不顺便优化措辞或重排消息 |
| 统一组装 | 组织场景规则、用户要求、指导内容、材料、工具定义及历史 | 业务执行器提供类型化输入，不拼接模型指令 |
| 场景规则 | 分离公共规则与代码专项、代码 Agent、报告及验证规则 | 现有代码任务继续执行固定版本、只读、引用及容量限制 |
| 纠正指令 | 执行器提供未提交结果、重复请求等事件，由组装层选择正文 | 不改变触发条件、次数、顺序及终态 |
| 工具描述 | 由结构化能力定义提供名称、用途、参数约束及说明，经模型协议适配生成工具定义 | 描述与执行校验共享约束来源，文案不能扩大执行权限 |
| 公共调用 | 继续复用容量、额度、重试、请求留存和调用记录 | 不合并业务语义不同的专项、Agent 和报告执行器 |

初步采用模板文件及清单，不新增系统提示词数据库表、在线编辑、发布、切换或回滚页面。Git 管理修改历史，资源随应用发布。现有用户提示词版本、用途校验及冻结机制保持原样。模板加载采用发布期固定资源，不增加运行中热更新；缺失资源、未知变量或不兼容声明须在启动检查或构建检查中明确失败，不静默回退为空提示词。

模板版本、工具定义版本与未来插件定义版本分别表达。实际请求快照仍是历史阅读依据，不用当前模板重建历史请求。标识如何关联现有记录在实施时核对，优先兼容既有结构，不为标识预设数据库迁移。标识不注入模型正文，不影响容量与模型行为。

## 3. 为插件建设保留的空间

- 组装层接收本次可用能力集合，不自行发现插件、绑定连接或决定授权。现有内置工具通过描述提供边界接入，未来可增加插件来源。
- 工具元数据与模型供应商的消息格式分离，未来 MCP 出口可复用能力定义，而不是解析现有模型请求反推工具信息。
- 公共规则不强制仓库、SHA 或代码行号；这些约束仍属于现有代码场景。未来接口证据可提供业务对象及取得时间，本次不修改现有证据协议。
- 区分系统边界、任务要求、能力指南和返回材料。插件指南可补充方法，不能覆盖授权及输出约定；接口返回与源码一样属于材料。
- 组装边界允许后续追加操作说明及执行反馈，不要求所有能力文档在首轮全部展开。本次只保留接口空间，不实现动态发现。
- 认证、凭证、HTTP 映射及实际授权留在执行能力边界，不能作为工具说明全部送入模型。

本次不实施插件导入、统一插件执行器、MCP、插件任务入口、通用证据存储或公共 Agent 循环提取，不提前固定插件 JSON 正式字段。

## 4. 保持现有功能的实施原则

第一轮以可观察行为等价为目标，正文抽取与行为优化分开提交。先建立改造前固定输入和输出基线，再逐场景替换；不能从新实现生成期望值来证明自身等价。

| 验证面 | 必须保持或核对的内容 |
| --- | --- |
| 实际模型请求 | system/user 正文逐字一致，包括空白、换行、截断标记；消息角色、顺序、工具历史、工具名称及参数不变 |
| 工具定义 | 序列化后的名称、说明、Schema、默认值、边界及示例等价；不能以 JSON 对象键顺序差异掩盖字段或数组变化 |
| 容量与分片 | 同一输入的计量、输出预留、容量判定、专项切分边界一致；覆盖临界容量，避免资源文件末尾换行造成行为变化 |
| 执行控制 | 传输重试与协议纠错分别核对；次数、额度、期限、取消、迟到响应保护及结果发布不变 |
| 历史与冻结 | 已接受任务的用户规则不变；旧请求原样读取；模板固定加载，Agent 多轮不切换资源版本；不新增中断恢复 |
| 结果与页面 | 专项 JSON 校验、Agent 显式提交及引用校验、报告来源引用和下载保持一致；不修改已有 API 与页面交互 |
| 部署 | 模板实际进入构建产物并可从打包应用加载；不依赖开发机绝对路径、不新增运行依赖 |

即使输入完全等价，真实模型输出仍可能波动；不能承诺模型逐字输出一致。工程等价验证用于排除重构引入的请求与控制变化，真实使用验证用于核对结果可用性，分别记录。

验证矩阵至少包括：问题文件／差异审查、设计模式、耦合度、完整文件与分片、格式纠错；Agent 首轮、工具往返、重复请求提示、未提交结果提示、正常及材料不足提交、取消与硬限制；报告无规则／专用规则／COMMON 规则及混合来源；连通验证及工具协议双轮验证。覆盖无可选内容、中文、多行正文、边界长度、缺失材料和历史记录阅读。

优先复用现有组装、专项校验、执行器、工具协议及报告测试，新增真正验证迁移等价和边界的检查，不机械复制实现。先跑受影响套件，再在集成完成时运行后端回归；未改前端不默认重做全部视觉验收。既有失败独立记录，不能通过修改预期掩盖新增差异。

真实模型和目标环境验证在明确资源与操作范围后执行，至少核对三类专项、代码 Agent、报告及两类模型验证入口。未执行时保持对应验收未完成，不以单测代替实际使用。涉及服务切换时沿用现有运维流程，不终止在途任务；资源与代码作为同一发布单元回退，不单独替换模板造成版本混搭。本计划不授权实际启停、部署或数据库操作。
