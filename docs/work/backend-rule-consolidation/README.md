# 后端规则同源维护改造

日期：2026-11-01。状态：规划完成，实施 todo。基于 dev `146139f` 的静态检查；本轮仅编写计划。业务语义以[业务契约](../agent-redesign/business-contract.md)为准，前后端一致性通过该契约及相关接口文档约束。

## 1. 范围与规模

目标是减少同一后端规则在提示词、结构定义和校验代码中的独立维护，使修改规则时有明确的权威入口。本次属于局部、跨若干类的维护性重构，规模中等偏小：涉及专项协议、Agent 提交、报告引用及两项公共辅助逻辑，预计影响约 15–25 个生产代码或资源文件，另有相关测试；此为规划估算，不是文件数量限制。

输出契约是主要工作量，不能仅提取常量就认定完成；但无需新增业务模块、数据库表、API 或运行依赖。不设大型阶段里程碑，使用三个可独立审阅的小任务，测试并入各任务。验收以相关测试和最终后端全量回归通过为准，不要求真实模型调用、服务启停、数据库操作、页面视觉或部署验收。

不改前端，不生成跨语言类型，不建设通用规则引擎、配置语言、插件框架或在线契约管理。不重写执行循环、任务状态机、容量算法和历史记录读取。

## 3. 实施设计

### 3.1 输出契约

各业务保留独立契约，优先采用小型 Java 定义和现有模板机制，允许少量共享字段描述与校验辅助类。具体类名在实施时确定，不新增独立模块或引入通用 Schema 运行库。

- 结构规则在一个位置声明：字段类型、必填／可选、空值与空数组语义、枚举、长度和数量限制、未知字段策略。模型可见的结构说明及运行时结构检查从这些声明取得规则。
- 保留现有结果 record 作为业务载体，避免另建重复 DTO；如映射仍需要显式字段，增加契约与载体的一致性检查，不让字段清单静默分叉。数组缺失检查必须发生在 null 被归一化为空数组之前。
- 条件及证据规则使用业务代码实现。每条规则将模型说明、适用条件和校验入口放在同一归属位置，由对应输出契约选用；不要求把动态业务逻辑编码为 JSON。
- 模板保留任务目标、分析方法和段落编排；字段、枚举、数量及条件要求通过契约提供的片段插入。清理其他模板、工具说明与纠错文案中的独立规则副本，不能只替换一份主模板。
- 共用的是可证明相同的基础能力；专项材料位置、Agent 的已发送材料和报告冻结来源继续使用各自上下文，不统一成一种证据对象或一种引用格式。

专项：问题文件／差异共用结构，分别选择 changeRelation 和材料侧规则；模式保留至少一处目标依据；耦合保留 dependencyId 的实际事实集合检查。三类结果的空数组、可选 evidence、建议字段等现有差异逐项保留。

Agent：`submit_result` 的工具定义和 `AgentSubmission` 消费同一提交契约。长度、数组上限及字段不再各写一份；保留 ANSWERED 有正文实际使用的有效引用、INSUFFICIENT_EVIDENCE 有未解决事项、未使用引用裁剪及多错误诊断行为。真实 materialId、材料范围与发送资格由上下文校验。

报告：仅建立轻量引用规则，统一标记识别、来源序号范围和最低引用要求的归属；继续输出 Markdown，不引入专项 JSON 结构。

### 3.2 提示词版本解析

抽取可跨 service／report 使用的基础版本解析：版本存在、归属正确、正文非空。专项和 Agent 未指定版本时使用当前版本；报告必须同时显式选择提示词与版本。将这些策略留在入口或显式参数中，不能让报告隐式回退当前版本。保留既有错误码和对外诊断语义，避免统一辅助类后改变失败分类。

### 3.3 模型快照

提取三类入口共同的模型快照构造逻辑。保留每个场景的外层快照结构、字段顺序、字段存在性、null 表达、默认协议和版本字段；确有差异时显式表示，不用统一默认值覆盖。凭据仍不写入快照；不改历史快照、不新增快照迁移。此项不顺带统一各场景模型准入要求。

## 4. 兼容与基线

实施前以当前生产实现和既有测试核对实际行为，补齐必要的固定正反例。复用 PAR 请求和工具基线，不重新捕获新实现的输出作为等价证据。

默认保持模型请求正文、空白、顺序、工具 JSON、容量计量、解析接受／拒绝范围、错误分类和执行控制不变。生成式说明应尽量保持原格式，不借机优化文案。若发现原提示、Schema 与校验存在冲突，先记录具体输入与两端行为，作为独立规则修正交负责人决定；不得默默收紧或放宽规则，也不得仅修改测试预期掩盖差异。

前后端的字段、枚举、可选性和状态语义继续以业务契约及相关接口文档约束。本次不改变这些语义；交付时记录后端权威实现入口，引用业务契约，避免复制另一份业务规则全文。
