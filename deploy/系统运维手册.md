# 系统运维手册

适用于当前新路线的离线部署。所有命令均在实际部署目录执行，示例为 `/opt/codereview`。Compose 服务名为 `app`、`mysql`，容器名为 `codereview-app`、`codereview-mysql`；Compose 命令使用服务名。

## 1. 启动、停止和重启

```bash
cd /opt/codereview

# 查看状态和最近应用日志。
docker compose -p codereview ps
docker compose -p codereview logs --tail=200 app

# 启动整套服务：MySQL 就绪后启动应用。
docker compose -p codereview up -d

# 只停止应用，MySQL 保持运行，适合维护与升级。
docker compose -p codereview stop app

# 启动应用。
docker compose -p codereview up -d app

# 仅重启应用，适合只修改外置 YAML 的情况。
docker compose -p codereview restart app

# 停止整套服务：先停应用，再停 MySQL。
docker compose -p codereview stop app
docker compose -p codereview stop mysql
```

维护前先停止提交新任务，等待运行任务完成，或在页面取消并确认结束。重启不会接续执行中断的任务，遗留任务与报告按现有规则收敛。日常启停不删除数据目录、镜像或网络。

整机重启后，已有容器按 `unless-stopped` 策略恢复；曾手动停止的容器仍需按上面的命令启动。每次启动后查看容器状态、应用日志和业务健康接口，不只检查页面能否打开。

## 2. 修改配置并使其生效

| 修改对象 | 操作 | 注意事项 |
| --- | --- | --- |
| `config/application.yml` | 静态校验后 `restart app` | 任务预算用于新建任务；页面参数需刷新浏览器 |
| `.env` 的端口、环境变量、资源上限，或 Compose 挂载 | `up -d --force-recreate <服务>` | 单纯 `restart` 不更新容器创建参数；数据库挂载变更须另做数据方案 |
| 模型、项目、提示词 | 管理界面保存并按要求验证 | 不通过 YAML 覆盖业务记录 |

先保存上一份配置。`config/application.yml.example` 是参考模板，修改它不会改变已有正式配置。改变数据库凭据时还须同步实际数据库账号，不能只改文件。

应用不读取系统环境变量；参数、仓库兜底令牌与 Git 镜像目录直接写在实际 YAML。Docker 的资源上限、端口与数据库初始化参数仍由 `.env`／Compose 管理。

```bash
# 应用已处于维护窗口，配置文件已准备好。
cp -p config/application.yml config/application.yml.before-change
# 只检查配置，不连接数据库、模型或仓库；不启动依赖服务。
docker compose -p codereview run --rm --no-deps app --check-config
# 检查通过后重启；失败则恢复原 YAML，查明原因后再操作。
docker compose -p codereview restart app
```

修改 `.env` 中应用容器参数时，改用：

```bash
docker compose -p codereview up -d --force-recreate app
```

LLM 参数建议、联动关系与单位见[系统部署手册](系统部署手册.md)第 2 节。普通模型连通验证与双轮工具验证有独立浏览器等待时间；不要只增加后端期限而保留过短的前端等待。

## 3. 数据与备份

| 内容 | 位置 | 保留要求 |
| --- | --- | --- |
| MySQL 数据文件 | `data/mysql` | 升级继续使用原绝对路径；不在运行中直接复制文件作为一致性备份 |
| Git 镜像缓存 | `data/git-mirrors` | 可重建，但重建会消耗时间和存储 |
| 实际配置 | `.env`、`config/application.yml`、`docker-compose.yml` | 与数据库、镜像版本一起保存，限制读取权限 |
| 数据库导出 | `backups/*.sql.gz` | 脚本日常保留 7 天；升级封存副本须放到独立目录 |

```bash
bash scripts/backup.sh
```

当前备份脚本导出新路线业务库，存在兼容库时也导出兼容库，并保存 `.env`。业务库缺失或导出失败会停止。YAML、Compose 和脚本需按下节另行封存。定时备份并未自动安装；确需定时运行时由运维另行配置。

备份文件存在、非空或 gzip 校验通过，均不代表已验证数据库可恢复。升级前应将选定导出恢复到独立临时库，核对关键表及记录；恢复演练不使用正式运行库。未经恢复核对，不将备份标记为可用回退点。

## 4. 新版本部署并保留数据

### 4.1 适用条件

本流程用于同一新路线内、发布说明明确支持的版本升级。九月旧路线转换到当前独立新库见部署手册第 6 节；不得直接套用本流程假定旧业务记录会自动转换。

每个发行版本必须记录：源版本范围、目标版本、数据库迁移内容、配置新增／变更、停机影响、旧程序能否读取升级后的数据库，以及回退方式。缺少这些信息时先补齐发布说明。当前记录未完成内网升级演练，不承诺任意历史版本直接升级。

### 4.2 准备新包

新包解压到临时目录，例如 `/opt/codereview-staging/<版本>`，核对其中校验和与发行说明。正式运行位置仍为原部署目录。以下命令中的 `NEW` 必须替换成已解压的新包绝对路径，不能指向正式目录。

```bash
cd /opt/codereview
INSTALL=$(pwd -P)
NEW=/opt/codereview-staging/<版本>/codereview-offline-<版本>
(cd "$NEW/images" && sha256sum -c SHA256SUMS.txt)
```

检查新 Compose 的数据库挂载仍指向 `"$INSTALL/data/mysql"`。不要把旧 `.env` 丢掉，也不要使用新包中的空 `data/mysql` 替代原数据目录。

### 4.3 停止写入并封存

确认运行任务已结束，进入维护窗口：

```bash
docker compose -p codereview stop app
bash scripts/backup.sh

SNAPSHOT="$INSTALL/upgrade-snapshots/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$SNAPSHOT"
chmod 700 "$SNAPSHOT"
cp -p .env docker-compose.yml "$SNAPSHOT/"
cp -p config/application.yml "$SNAPSHOT/application.yml"
cp -a scripts "$SNAPSHOT/scripts"
cp -p backups/*.sql.gz "$SNAPSHOT/"
docker inspect --format '{{.Config.Image}} {{.Image}}' codereview-app > "$SNAPSHOT/app-image.txt"
sha256sum "$SNAPSHOT"/*.sql.gz > "$SNAPSHOT/SHA256SUMS.txt"
```

从封存目录中选定本次时间对应的业务库导出，执行 `gzip -t` 并完成独立恢复核对。目录中可能含历史导出，不按文件名猜测恢复对象。记录明确的 `OLD_TAG`，确认对应旧镜像仍在本机。封存目录包含敏感信息，不发布到公开仓库或 Release。

### 4.4 更新程序与合并配置

以下仅覆盖程序交付文件，保留正式 `.env`、实际 YAML、`data/` 和备份。先核对临时包路径，`NEW` 与 `INSTALL` 不得相同。

```bash
cp -a "$NEW/images/." "$INSTALL/images/"
cp -a "$NEW/scripts/." "$INSTALL/scripts/"
cp -p "$NEW/docker-compose.yml" "$INSTALL/docker-compose.yml"
cp -p "$NEW/config/application.yml.example" "$INSTALL/config/application.yml.example"
cp -p "$NEW/系统部署手册.md" "$NEW/系统运维手册.md" "$NEW/00-先读我.md" "$INSTALL/"
```

逐项合并发行说明要求的新配置到 `config/application.yml`，不要用模板整文件覆盖已有配置。内网地址、凭据、端口与资源上限继续使用正式值。新旧模板或配置项不一致时先处理差异，再继续。

本版停用应用环境变量读取。若旧文件含 `${GITEA_TOKEN:}`、`${GITHUB_TOKEN:}`、`${GITEA_MIRROR_DIR:...}` 或 `${DB_URL}`／`${DB_USER}`／`${DB_PASSWORD}`，先将引用替换为实际值；镜像目录通常为 `/app/data/git-mirrors`。旧 `.env` 中的仓库令牌不再注入应用；前置体检发现这些旧引用会停止部署。脚本不会自动复制凭据或覆盖已有 YAML。

```bash
cd "$INSTALL"
bash scripts/deploy.sh --tag <新版本>
```

脚本检测应用仍在运行时拒绝升级；应用已停止后，导入镜像、静态检查配置并备份数据库，再启动新应用。Flyway 对同一新路线只执行尚未应用的增量脚本，校验已有历史。迁移成功也不代表业务数据正确，须执行下一步核对。

### 4.5 验证并恢复使用

核对新镜像版本、MySQL 原挂载目录、配置加载结果和 `/api/v2/health`；检查 `agent_schema_history` 中的执行结果。确认旧项目、模型、提示词、历史结果与报告仍可读，执行一次新的审查、反馈及报告流程。通过后才解除维护并允许新任务写入。

升级失败时保持应用停止，保存日志和升级后数据库现场；不要删除迁移历史、执行 Flyway repair、清库重试或自动换旧镜像。按下一节判断恢复方式。

## 5. 失败恢复与回退

### 5.1 数据库和配置均兼容旧程序

先依据发行说明确认兼容性，必要时恢复旧版本可读取的 YAML。确认明确旧镜像版本后执行：

```bash
bash scripts/rollback.sh --tag <明确旧版本> --schema-compatible
```

此脚本只切换应用镜像，不恢复 YAML、数据库、Compose 或脚本。`previous` 只是可被再次部署覆盖的标签，不能替代版本记录。若当前 MySQL 健康，脚本会先备份；备份失败则停止回退。

### 5.2 数据库结构与旧程序不兼容

需要同时恢复已核对的升级前数据库、旧配置、旧 Compose／脚本和旧镜像。恢复升级前备份会丢弃备份之后的新写入；如升级后已允许用户操作，必须先导出并安排这些数据的处理，再决定恢复。未确认数据范围或备份恢复结果时，保持应用停止并交由维护人员处理。

以下步骤只适用于明确恢复当前新路线的 `ai_code_review_agent`，不适用于九月旧路线。恢复前停止所有会连接该库写入的应用，封存升级失败现场，确认 `.env` 的 MySQL root 密码与当前数据库匹配。`DUMP` 必须是独立恢复核对通过的升级前导出，`SNAPSHOT` 为对应封存目录。

```bash
cd /opt/codereview
docker compose -p codereview stop app
# 以下路径必须替换成已核对的准确路径。
SNAPSHOT=/opt/codereview/upgrade-snapshots/<备份时间>
DUMP="$SNAPSHOT/ai_code_review_agent-<导出时间>.sql.gz"
gzip -t "$DUMP"
# 仅加载当前数据库连接口令，不执行 .env 中的任意 shell 内容。
. scripts/common.sh
load_env
```

下一组命令会删除当前新路线库并恢复升级前状态，只有已确认可丢弃升级后写入且持有可恢复备份时才能执行。任何一步失败都停止，不继续启动应用。

```bash
# 密码仅通过容器环境传入；不要开启 shell 命令跟踪。
docker exec -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" codereview-mysql mysql -uroot -e   'DROP DATABASE ai_code_review_agent; CREATE DATABASE ai_code_review_agent CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;'
# 单独在 bash 中启用管道失败检查，不能忽略导入失败。
set -o pipefail
gzip -dc "$DUMP" | docker exec -i -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD"   codereview-mysql mysql -uroot ai_code_review_agent
```

数据库导入成功后，再恢复对应配置和旧程序。若 MySQL 账号在升级期间变更，还需核对账号及权限；业务库导出不包含 MySQL 系统账号。

```bash
cp -p "$SNAPSHOT/.env" .env
cp -p "$SNAPSHOT/application.yml" config/application.yml
cp -p "$SNAPSHOT/docker-compose.yml" docker-compose.yml
cp -a "$SNAPSHOT/scripts/." scripts/
# 核对恢复后的 .env 指向已记录的旧镜像，再启动。
docker compose -p codereview up -d app
```

检查旧版本健康、历史记录和模型／仓库连接。恢复完成前不解除维护。以上是恢复操作说明，当前尚未在目标内网完成恢复演练。

## 6. 常见问题

| 现象 | 处理 |
| --- | --- |
| 模型调用超时 | 核对公共响应上限、Agent 单次上限、总期限及网关超时；查看实际调用记录 |
| 连通验证或工具验证页面先超时 | 核对独立浏览器等待与后端验证期限；修改后重启应用并刷新页面 |
| 429、502、503、504 或连接失败 | 查看重试次数及网关等待要求，先核对并发与容量；重试计入预算 |
| 未知配置键或静态校验失败 | 对照新模板及发行说明检查键名、单位、范围和参数联动；不要跳过校验 |
| 数据库身份／迁移校验失败 | 保留日志和数据，核对实际库名、版本及历史；不要改历史表或删除迁移记录 |
| 换目录后历史数据为空 | 先停止应用，核对 MySQL 绑定挂载的原绝对路径；不要再创建或覆盖数据库 |
| 应用未就绪 | 查看 `docker compose -p codereview logs --tail=200 app` 和 MySQL 状态；失败后不自动回退镜像 |

排障材料只提供版本、状态、必要日志和脱敏配置。脱敏范围包括数据库密码、仓库／模型令牌和授权头；只删名为 `password` 的行并不足够。

## 7. 停用与卸载

日常停止使用第 1 节的 `stop` 命令。如需移除本项目的容器和网络，确认已停止写入并保存备份后执行：

```bash
cd /opt/codereview
docker compose -p codereview down
```

当前数据库使用宿主机绑定目录，以上命令保留 `data/mysql`、配置和备份。彻底删除部署目录会同时删除这些资料，不属于普通卸载或升级步骤；执行前另行确认对象与恢复副本。共享服务器上不运行全局 Docker 清理命令。
