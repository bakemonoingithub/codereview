# 系统部署手册

适用于离线 Docker 部署。目标平台沿用已验证的 CentOS 7.6、Docker 20.10.24、Compose v2.17.2；新版本的目标内网部署仍需单独验收。先按场景选择入口：

| 场景 | 阅读位置 |
| --- | --- |
| 首次安装，使用空数据库 | 本手册第 1–5 节 |
| 九月旧系统切换到当前新路线 | 本手册第 6 节 |
| 当前新路线更新版本并保留数据 | [系统运维手册](系统运维手册.md)第 4 节 |
| 启动、停止、重启与配置生效 | [系统运维手册](系统运维手册.md)第 1–2 节 |

## 1. 确定部署目录并解压

新安装使用固定目录，例如 `/opt/codereview`。数据库文件位于部署目录的 `data/mysql`；以后升级沿用这个目录。版本包解压到临时准备目录，升级时不得直接从另一个空目录启动。

```bash
mkdir -p /opt/codereview
# 将 <版本> 替换成实际版本；首次安装确认目标目录为空。
tar xzf codereview-offline-<版本>.tar.gz --strip-components=1 -C /opt/codereview
cd /opt/codereview
```

如果已有 `codereview-app`／`codereview-mysql`，先按第 6 节或保留数据升级流程处理。当前固定容器名和网络名，不支持直接并排启动两套。

## 2. 填写部署前配置

1. 复制 `.env.example` 为 `.env`，按目标环境填写端口与资源限制。三个数据库密码字段可留空，由首次部署生成；已有数据目录时必须使用与其配套的原 `.env`，不得重新生成。
2. 编辑 `config/application.yml.example`，将 `git.gitea.hosts` 改为实际仓库的 `host[:port]`。数据库占位符保留，由部署脚本替换。
3. 按本节下表审阅 LLM 参数。尚无模型性能数据时，表中值仅作为试运行起点。

```bash
cp .env.example .env
vi .env
vi config/application.yml.example
```

| 配置位置 | 配置内容 | 生效方式 |
| --- | --- | --- |
| `.env` | 端口、应用／MySQL 内存、Java 堆、凭据环境变量 | 重新创建受影响容器 |
| `config/application.yml` | 模型调用、任务、Agent、Git、缓存和前端公开参数 | 重启应用；页面参数另需刷新浏览器 |
| 管理界面与数据库 | 模型地址、名称、令牌、真实窗口／输出能力，项目、提示词 | 按业务配置规则保存、验证；不由旧 `AI_BASE_URL` 等环境字段初始化 |

首次部署只生成一次 `config/application.yml`。之后编辑实际 YAML；只改 `.example` 或 `.env` 不会自动更新已生成的数据库连接配置。数据库账号或密码变更时，须同时核对 YAML、`.env` 与实际账号。

当前容器模板包含以下内网试运行建议：

| 参数 | 试运行值 |
| --- | --- |
| `agent.model.connect-timeout-seconds` | 30 秒 |
| `agent.model.max-read-timeout-seconds` | 600 秒 |
| `agent.budget.model-timeout-seconds` | 600 秒 |
| `agent.model.transport-retries` | 额外 3 次，首次请求不计入 |
| `agent.model.retry-base-millis`／`retry-multiplier`／`retry-max-millis` | 3000 毫秒／2／30000 毫秒 |
| `agent.model.retry-jitter-ratio`／`retry-check-millis` | 0.2／1000 毫秒 |
| `agent.model.connectivity-validation-timeout-seconds` | 连通验证总期限 600 秒 |
| `agent.model.tool-validation-timeout-seconds`／`tool-validation-output-tokens` | 工具验证每轮总期限 1200 秒／1024 token，共两轮 |
| `agent.model.global-concurrency`／`per-task-concurrency` | 2／1 |
| `agent.task.deadline-minutes`／`agent.budget.deadline-minutes` | 专项／Agent 各 120 分钟 |
| `agent.report.generation-timeout-minutes` | 30 分钟 |
| `agent.budget.network-attempts`／`agent.model.task-call-limit` | 192／200 次，失败与重试也计数 |
| `app.ui.model-validation-timeout-millis`／`agent-validation-timeout-millis` | 浏览器验证请求 900000／2700000 毫秒 |

单次 Agent 调用同时受公共响应上限、Agent 单次上限、任务剩余时间及网关限制约束。网关必须允许相应时长。重试采用递增等待和随机错峰；`Retry-After` 是网关要求的最短等待，不受本地 30000 毫秒上限截短，剩余期限不足时结束。等待期间按 `retry-check-millis` 检查取消和期限。认证、参数及上下文错误不作为网络错误反复请求。

浏览器连通验证等待须大于后端连通验证总期限；工具验证等待须大于两轮后端期限之和，并留出网络及保存结果的时间。启动校验检查这两组关系。普通业务请求仍为 30 秒；后台任务依靠轮询查看，不占用一个长页面请求。

## 3. 检查环境与文件

```bash
bash env-check.sh
(cd images && sha256sum -c SHA256SUMS.txt)
```

校验和须全部为 `OK`。检查实际部署分区和 Docker 数据分区余量、18080 的占用、资源配额及容器运行状态。宿主机已有 MySQL 不影响本包内部网络的 MySQL；本包不发布 3306。

按内网规则申请实际应用端口的访问权限，并确认应用容器可访问 Gitea 和模型网关。本套脚本不修改防火墙、不清理其他项目的镜像或数据，也不重启整机 Docker 服务。

## 4. 首次部署

确认使用空数据目录，且已填写 Gitea host 后执行：

```bash
bash scripts/deploy.sh --tag <版本>
```

脚本依次生成配置、检查环境、导入镜像、使用新镜像执行 `--check-config` 静态校验、准备 MySQL 与新库账号、备份并启动应用。静态校验不连接数据库、仓库或模型；应用启动后才检查数据库身份并执行增量建表脚本。

应用业务库为 `ai_code_review_agent`。Compose 仍保留兼容库初始化字段，旧库不被新应用使用。空库启动日志中的 Flyway「迁移」指自动建表，不要求导入旧测试数据。

镜像明确读取 `/app/config/application.yml`，对应宿主机 `config/application.yml`。缺文件、配置非法或新库身份不匹配时停止启动。应用未按时就绪时，脚本尝试停止应用并保留数据库；不自动切回旧镜像。

## 5. 验证部署结果

```bash
docker compose -p codereview ps
docker compose -p codereview logs --tail=200 app
curl -fsS http://127.0.0.1:18080/api/v2/health
```

若修改端口，将 `18080` 替换成实际端口。容器就绪后访问页面，配置内网模型及项目，执行模型连通验证和 Agent 工具验证，再验证一次专项、Agent、反馈及报告流程。健康检查通过只证明服务就绪，不能替代业务验收。

失败时保留日志、准确镜像版本和脱敏配置，按运维手册处理。密码与令牌不得直接附在排障材料中。

## 6. 从九月旧系统切换到新路线

`v20260920c-d114f62` 属于旧路线；当前新路线使用独立的新库。两者不是同一条数据库迁移链，新版本不会自动转换旧项目、审查和报告记录。

若旧测试数据只需封存：在旧目录停止写入并使用旧版本配套方式备份旧库、`.env`、实际 YAML 和旧镜像版本；确认恢复副本可用后停止旧应用及其 MySQL。新版本可在独立目录按首次部署流程初始化空库，保留旧目录和备份，不删除旧资料。两套固定容器名不能同时使用，切换前须核对现有容器及挂载，确认新目录不会被误认为保留数据升级目录。

新库中的模型、项目和提示词需重新配置或通过另行确认的导入方案准备。如要求将旧业务记录转换后继续使用，须先制定专门的数据迁移方案；不要把旧库改名后直接交给新程序。

本手册的静态校验、脚本检查和目标环境真实部署分别记录；未执行的内网操作不标记为已验证。
