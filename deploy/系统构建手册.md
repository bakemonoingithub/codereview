# 系统构建手册

* 本手册说明如何通过 **GitHub Actions** 构建离线部署包。
  * 支持 PowerShell 命令行和 IntelliJ IDEA 两种标签操作方式；
  * 推送标签会实际触发在线构建和 Release 发布。

* 其他手册
  * 首次部署见[系统部署手册](系统部署手册.md)
  * 启停、配置生效和保留数据升级见[系统运维手册](系统运维手册.md)。

## 1. 构建方式介绍

### 1.1 构建过程

本项目仓库为 [bakemonoingithub/codereview](https://github.com/bakemonoingithub/codereview)，发布分支为 `dev`，流程定义见 [release.yml](../.github/workflows/release.yml)。

GitHub Actions 在 GitHub 提供的 Ubuntu 构建机上读取指定提交，执行前后端检查、构建应用镜像，组合 MySQL 镜像、部署脚本、配置模板、手册、源码快照和校验和，再上传到 GitHub Releases。

使用本流程时，本机只需完成 Git 操作和结果下载，无需在本机构建 Docker 镜像。

| 行为 | 结果 |
| --- | --- |
| 仅推送 `dev` 分支 | 更新远端源码，不自动打包 |
| 推送以 `v` 开头的标签 | 自动执行「构建离线部署包」 |
| 在 Actions 页面选择 Run workflow | 手动执行，需要仓库写权限；正式交付优先使用已固定提交的标签方式 |

标签固定本次打包的源码提交。未提交或未被标签包含的本地改动，不会进入在线构建。

### 1.2 公开仓库与私有仓库的区别

以下规则核对于 2026-10-28，后续以 [GitHub Actions 官方计费说明](https://docs.github.com/en/billing/concepts/product-billing/github-actions)为准。

| 场景 | GitHub Free 的相关规则 |
| --- | --- |
| 公开仓库使用标准 GitHub 托管构建机 | 构建用时免费；本项目当前使用标准 `ubuntu-latest` |
| 私有仓库使用标准 GitHub 托管构建机 | 每账号每月包含 2000 分钟及 500 MB Actions 产物存储，账号内共享；不能当作每个仓库各有一份 |
| 使用大型付费构建机 | 公开仓库也会收费；当前流程未使用 |
| 依赖缓存 | 每仓库默认包含 10 GB；主动提高容量上限后，超出免费部分可能收费 |

本项目将部署包放在 Releases，未保存为 Actions Artifacts。

Releases 当前要求每个附件小于 2 GiB，每个 Release 最多 1000 个附件，不限制单个 Release 的附件总大小和下载带宽，见 [Releases 官方限制](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas)。

## 2. 第一步：确认配置、提交并推送源码

### 2.1 打包前核对

1. 确认打开的是 `H:\myProjects\aiCodeReview\code`，分支为 `dev`。
2. 核对[容器配置模板](config/application.yml.example)中的 LLM 超时、重试、并发和预算，以及 Gitea 主机配置。当前 Gitea 主机为 `192.104.224.172`；`/gitea/` 子路径从项目仓库地址推导。
3. 核对[部署环境模板](.env.example)中的端口和资源限制。模型地址、名称、令牌、窗口及最大输出在部署后由「模型管理」维护，不需要写进构建配置。
4. 核对前后端检查结果与已知问题，当前流程的前后端单测失败会阻止出包。
5. 核对将要提交和公开发布的文件。真实数据库密码、仓库／模型令牌和本机实际运行配置不得进入公开仓库或部署包。
6. 如版本涉及数据库结构变化，准备源版本范围、迁移内容、配置变更、停机影响和回退兼容说明。当前工作流的 Release 文案是通用部署说明，不会自动生成数据库升级说明。

本手册位于 `deploy/` 下，也需要提交到发布提交，才能随包交付。

### 2.2 PowerShell 操作

在 PowerShell 中进入主工作树，先检查分支、待提交文件和远端地址：

```powershell
Set-Location 'H:\myProjects\aiCodeReview\code'
git status --short --branch
git branch --show-current
git remote -v
git diff --check
```

分支应为 `dev`，`origin` 应指向本项目 GitHub 仓库。任一命令报错、发现意外文件或分支不符时，先处理原因，不继续发布。

按实际范围提交文件，以下只演示。

```powershell
git add -- 'deploy/系统构建手册.md' 'deploy/config/application.yml.example'
git diff --cached --stat
git diff --cached
```

确认暂存内容后提交；如果本次没有新改动，跳过提交命令，不创建空提交。

```powershell
git commit -m 'docs(deploy): 完善系统构建手册并确认部署配置'
```

获取远端状态，再推送 `dev`：

```powershell
git fetch origin
git status --short --branch
```

若显示远端有本地尚未合入的提交，先按项目流程处理差异。不要强制推送覆盖远端历史。确认可以推送后执行：

```powershell
git push origin dev
```

推送成功后核对本地与远端分支的提交号：

```powershell
git status --short --branch
git rev-parse HEAD
git ls-remote origin refs/heads/dev
```

### 2.3 IntelliJ IDEA 操作

1. 打开 `H:\myProjects\aiCodeReview\code`，核对 Git 分支为 `dev`。
2. 打开 Commit 窗口（Windows 默认 `Ctrl+K`），检查差异，勾选本次确认的文件并填写提交说明。
3. 执行 Commit；没有新改动时跳过此步。
4. 打开 Push 窗口（Windows 默认 `Ctrl+Shift+K`），核对推送目标为 `origin/dev`，检查待推送提交后执行 Push。
5. 在 Git 日志与 GitHub 的 `dev` 分支页面核对最新提交一致。

参考 [JetBrains 提交与推送说明](https://www.jetbrains.com/help/idea/commit-and-push-changes.html)。

## 3. 第二步：创建并推送打包标签

命令行与 IDEA 任选一种方式，不重复创建同名标签。推荐名称为 `v日期-短提交号`，例如 `v20261028-abcd123`；

示例提交号需替换成实际值。标签必须以小写 `v` 开头。

### 3.1 PowerShell 方式

以下命令使用执行当天的日期和当前提交号生成标签名：

```powershell
$releaseTag = "v$(Get-Date -Format 'yyyyMMdd')-$(git rev-parse --short HEAD)"
$releaseTag
git tag --list $releaseTag
git ls-remote --tags origin "refs/tags/$releaseTag"
```

最后两条查询都无匹配输出时，表示该名称未在本地或远端使用。

```powershell
git tag -a $releaseTag -m "内网离线部署包 $releaseTag"
if ($LASTEXITCODE -ne 0) { throw '创建标签失败，停止发布' }

git rev-parse HEAD
git rev-parse "${releaseTag}^{commit}"
```

两个提交号应一致。确认后执行：

```powershell
git push origin $releaseTag
if ($LASTEXITCODE -ne 0) { throw '推送标签失败，请先检查原因' }
```

标签推送成功即会触发 Actions；仅在本地创建标签不会触发。

### 3.2 IntelliJ IDEA 方式

1. 在 Git 日志中找到已推送的 `dev` 最新提交，记录短提交号。
2. 选择主菜单 Git → New Tag，仓库根目录选当前 `code` 工作树，提交填 `HEAD`，标签名按日期和实际短提交号填写。
3. 在 Message 中填写发布说明，单击 Create Tag；不要勾选 Force。填写说明后创建的是带说明的标签，便于后续随当前分支推送。
4. 在日志中核对标签位置。若 IDEA 的标签列表提供 Push to origin，选中本次标签并推送。
5. 若没有单标签入口，打开推送窗口，勾选 Push tags，选择 Current Branch，核对推送范围后执行。不要选择 All；无法确认是否夹带其他标签时，改在内置终端精确执行 `git push origin <实际标签名>`。
6. 在 GitHub 的标签页面确认标签存在，且指向预期提交。

普通代码推送默认不发送标签；Message 留空创建的普通标签，不依赖当前分支选项自动推送。菜单名称可能随 IDEA 版本变化，缺少界面入口时使用终端方式。

操作依据见 [JetBrains 标签说明](https://www.jetbrains.com/help/idea/use-tags-to-mark-specific-commits.html)。

### 3.3 备用方式：Actions 手动触发

当前流程也配置了 `workflow_dispatch`，仓库默认分支为 `dev`。在 Actions 中选择「构建离线部署包」→ Run workflow，选择 `dev`，输入唯一版本号或留空自动生成，再执行。手工填写 `version` 时不带前导 `v`，因为发布步骤会自行添加。

该方式需要仓库写权限，且流程文件必须存在于默认分支，见 [GitHub 手动运行说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。正式交付仍推荐先创建固定提交的标签；手动触发后，必须核对最终 Release 标签与运行记录的提交号一致，尤其是在构建期间 `dev` 又有新提交时。

同一版本不要同时使用标签与手动方式重复触发。当前发布脚本对已存在的 Release 会覆盖同名部署包附件，版本号不能复用于不同源码提交。

## 4. 第三步：查看结果并下载部署包

### 4.1 确认构建结果

打开 [GitHub Actions](https://github.com/bakemonoingithub/codereview/actions)，选择本次标签或版本对应的「构建离线部署包」。核对运行记录中的提交号与标签一致。

| 作业／步骤 | 成功条件与含义 |
| --- | --- |
| 后端单测 | 全量后端单测通过；失败则不执行构建作业 |
| 前端单测 | 安装依赖、前端单测通过；失败则不执行构建作业 |
| 类型检查（不阻塞） | 当前设置为允许失败；整体绿色不代表类型检查也通过，须单独查看并记录 |
| 构建离线包 | 构建应用镜像、拉取 MySQL、组装文件、校验必需内容并上传 Release 全部完成 |

本流程固定 `linux/amd64`，使用 Docker 镜像输出格式，并关闭 provenance／SBOM，服务于目标 Docker 20.10.24 的导入兼容。

流程文件改变时，以实际版本为准，不能用其他构建方式的成功代替本流程结果。

排队、运行中、跳过、取消均不代表打包成功。

### 4.2 下载正确的文件

打开 [GitHub Releases](https://github.com/bakemonoingithub/codereview/releases)，进入与本次标签完全一致的版本，从 Assets 下载：

```text
codereview-offline-<日期>-<短提交号>.tar.gz
```

标签名带前导 `v`，部署包文件名不带该前导字符。例如标签 `v20261028-abcd123` 对应 `codereview-offline-20261028-abcd123.tar.gz`。

不要将 GitHub 自动生成的 Source code ZIP／tar.gz 当作离线部署包，它们不包含本流程打包的 Docker 镜像。

### 4.3 核对包内内容与完整性

解压后应包含以下主要内容；其中 `<版本>` 为不带前导 `v` 的版本号。

| 内容 | 位置 |
| --- | --- |
| 应用镜像 | `images/codereview-app-<版本>.tar.gz` |
| MySQL 镜像 | `images/mysql-8.0.36.tar.gz`；镜像版本改变时按实际值 |
| 镜像校验和 | `images/SHA256SUMS.txt` |
| 部署脚本与环境检查 | `scripts/`、包根目录 `env-check.sh` |
| Compose 与部署环境模板 | `docker-compose.yml`、`.env.example` |
| 应用参数模板 | `config/application.yml.example` |
| 阅读入口与手册 | `00-先读我.md`、本构建手册、系统部署手册、系统运维手册 |
| 本次提交的源码快照 | `source-<版本>.zip` |

在 Linux 中进入解压后的部署包目录，执行镜像校验：

```bash
(cd images && sha256sum -c SHA256SUMS.txt)
```

镜像应全部显示 `OK`。该清单只校验 `images/` 中的镜像，不覆盖整个外层包或数据库备份。需要确认摆渡前后外层包一致时，可在 Windows 下载后先记录 SHA256，并在复制到介质或另一位置后再次计算比较：

```powershell
$bundlePath = 'C:\Downloads\codereview-offline-实际版本.tar.gz'
Get-FileHash -LiteralPath $bundlePath -Algorithm SHA256
```

校验失败时停止交付，重新下载或复制后复核。部署前再按部署手册检查环境和运行配置；打包成功不证明内网模型、仓库和数据库操作已通过验证。

## 5. 构建失败的处理

| 现象 | 处理 |
| --- | --- |
| 推送代码后没有运行记录 | 当前流程不由普通分支推送触发；核对本次 `v` 开头标签是否已推送到正确仓库 |
| 标签只在 IDEA 本地可见 | 精确推送本次标签，再检查 GitHub Tags 和 Actions |
| 单测失败、构建作业跳过 | 打开失败步骤，定位最早的有效错误；修复代码并通过检查后创建新提交和新标签，不通过跳过测试出包 |
| 镜像拉取、依赖下载或上传临时失败 | 先确认失败是否为外部暂态问题；可重跑同一次运行，运行仍绑定相同源码提交。不要因临时故障强制移动标签 |
| 标签名已存在 | 核对其提交和既有 Release；修复产生新提交时使用新标签，不覆盖已交付版本 |
| 手动触发按钮不可见 | 核对写权限、默认分支中的流程文件及 `workflow_dispatch` 配置；也可使用标签方式 |
| 出现用量或付款提示 | 核对仓库公开状态、构建机类型、缓存容量及账号预算；不要直接开会员 |
| Release 有包但配置不符合预期 | 比较运行提交号、标签、源码快照和模板；本地未提交修改不会自动进入包 |

## 6. 留存构建与交付记录

每次交付至少保存下表信息，便于核对内网使用的镜像与源码。

| 项目 | 记录内容 |
| --- | --- |
| 源码 | 分支、完整提交号、标签名 |
| 在线构建 | Actions 运行链接、结果、未通过或允许失败的检查 |
| 发布文件 | Release 链接、部署包文件名、大小及外层 SHA256 |
| 配置 | 随包模板版本、独立携带的实际配置版本，不在公开记录中保存凭据 |
| 数据库 | 支持的升级来源、迁移说明、回退兼容性；未演练项如实记录 |
| 交付验收 | 包完整性检查、内网部署／升级／恢复及业务测试分别记录结果 |

本手册提供构建操作说明。


## 7. 本地验证正式部署脚本（WSL + Docker Desktop）

本章使用包内原有的 `scripts/deploy.sh`，在本机验证首次部署全过程。

通过标准包括脚本体检、镜像导入、数据库与账号初始化、备份、应用启动及页面访问。

以下命令全部在本机 WSL 的 Ubuntu 终端执行。

### 7.1 准备 WSL 和 Docker Desktop

1. 启动 Docker Desktop，使用 Linux 容器模式。
2. 在 Docker Desktop 的 Settings → Resources → WSL Integration 中启用 Ubuntu 的集成，应用设置后从开始菜单打开 Ubuntu。
3. 在 Ubuntu 中检查 Docker，确认连接的是本机 Docker Desktop。

```bash
docker context show
docker info --format '{{.Name}} / {{.OSType}}'
docker compose version
```

WSL 发行版应为 WSL 2；检查方式与集成设置见 [Docker Desktop 官方说明](https://docs.docker.com/desktop/features/wsl/)。不需要在 Ubuntu 中再启动另一套 Docker Engine。

解压后的部署目录必须位于 WSL 的 Linux 文件系统，例如 `~/codereview-deploy-test-日期时间`。

包文件可以从 `/mnt/c/` 或 `/mnt/h/` 读取，但不能直接在这些 Windows 挂载目录里运行部署，当前正式脚本会拦截这类目录，MySQL 数据目录也需要 Linux 文件权限语义。文件系统选择参见 [Docker WSL 最佳实践](https://docs.docker.com/desktop/features/wsl/best-practices/)。

当前脚本要求部署分区可用至少 5 GiB、Docker 数据分区可用至少 8 GiB、WSL 当前可用内存至少 6 GiB。正式配置的应用／MySQL 上限为 4g／2g，还要为 Docker 和系统保留资源。

Docker Desktop 的数据目录位于其管理的 Linux 环境，未必能从 Ubuntu 中直接按相同路径访问。当前预检使用调用端的 `df` 检查 Docker 返回的数据目录；如果因此报告磁盘空间未知，应作为脚本对该环境的探测兼容问题记录并修复，不能注释体检、伪造目录或改用其他启动方式后宣称脚本通过。

### 7.2 确认不会占用已有项目

正式脚本固定使用项目 `codereview`、容器 `codereview-app`／`codereview-mysql` 和网络 `codereview-net`。不同 WSL 发行版连接同一 Docker Desktop 时，也会看到同一套容器；仅换一个终端或目录不能隔离这些名称。

```bash
docker ps -a --format '{{.Names}}' | grep -E '^codereview-(app|mysql)$'
docker network ls --format '{{.Name}}' | grep -x 'codereview-net'
```

没有匹配输出才继续新装验证。若已有同名资源，先核对归属、原部署目录及数据，再按运维手册处理。本章不自动停止、删除或挪用已有资源，也不改脚本固定名称来绕过冲突。

### 7.3 在 Linux 目录解压正式包

下载完整的 `codereview-offline-实际版本.tar.gz`，将下面的文件路径替换为 Windows 中的实际下载位置。

每次新装验证使用一个新目录；不要复制已有 `.env`、运行配置或数据库数据进来。

```bash
bundle='/mnt/c/Users/你的Windows账号/Downloads/codereview-offline-实际版本.tar.gz'
test_dir="$HOME/codereview-deploy-test-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$test_dir"
tar xzf "$bundle" --strip-components=1 -C "$test_dir"
cd "$test_dir"
pwd
df -PT .
```

逐条确认命令成功，当前目录应在 `/home/...` 等 Linux 路径下，而不是 `/mnt/c/...` 或 `/mnt/h/...`。

记下 `$test_dir`，后续日志、配置和数据都保留在此目录。

核对镜像包完整性：

```bash
(cd images && sha256sum -c SHA256SUMS.txt)
```

所有镜像显示 `OK` 后继续。本次只验证启动，保留包内已确认的 LLM 与 Gitea 参数；模型和项目可以在系统启动后填写，不要求本机能访问内网。

### 7.4 准备本机端口，直接执行正式脚本

在首次启动前，只修改解压测试副本的 `.env.example`：应用端口使用 18180，只绑定本机回环地址。若端口已占用，换成其他空闲端口，并在后续访问时使用同一数值。

```bash
sed -i \
  -e 's/^APP_PORT=.*/APP_PORT=18180/' \
  -e 's/^APP_BIND_IP=.*/APP_BIND_IP=127.0.0.1/' \
  .env.example
```

让脚本首次生成 `.env` 和数据库密码，不预先复制一份密码留空的 `.env`。当前脚本只会在 `.env` 不存在时自动生成 MySQL root 和兼容账号密码；已有空 `.env` 会导致体检失败。

下面的命令会实际导入镜像、创建本机容器、数据库、账号和备份。脚本询问是否启动时，核对端口与资源后输入 `y`。保留完整日志和脚本退出码：

```bash
set -o pipefail
bash scripts/deploy.sh 2>&1 | tee deploy-test.log
deploy_rc=${PIPESTATUS[0]}
printf 'deploy.sh 退出码：%s\n' "$deploy_rc"
```

退出码必须为 `0`，且日志出现部署完成，才进入结果核对。不能只看 `tee` 是否写出日志，也不能只看某个容器是否创建。任何报错先停止，保留 `.env`、实际 YAML、数据目录和日志；修复后从同一目录重测，不通过清空数据或更换启动入口掩盖失败。

本次应由脚本实际完成：环境体检 → 镜像装载 → 外置配置静态检查 → MySQL 就绪 → 新库与独立账号准备 → 备份 → 应用启动 → 健康检查。应用未就绪时，脚本会尝试停止应用并保留数据库，不自动回退旧镜像。

### 7.5 核对系统是否能正常打开

仍在同一个部署目录执行：

```bash
docker compose -p codereview ps
docker compose -p codereview logs --tail=150 mysql app
docker exec codereview-app curl -fsS http://127.0.0.1:8080/api/v2/health
docker exec codereview-app curl -fsS http://127.0.0.1:8080/api/v2/runtime-config
```

在 Windows 浏览器打开 `http://127.0.0.1:18180`。若脚本显示 WSL 的地址，仍按本次回环绑定与端口访问。

| 检查项 | 通过条件 |
| --- | --- |
| 正式脚本 | `deploy.sh` 退出码为 0，完整部署步骤成功，无跳过体检或手工替代步骤 |
| 容器 | 应用和 MySQL 均为 `healthy`，没有持续退出或反复重启 |
| 数据库健康接口 | 返回 `database=agent` 和当前身份版本 `schemaVersion=1`；身份版本不等于 Flyway 的迁移序号 |
| 公开配置接口 | 正常返回应用标题、请求超时与轮询参数 |
| 页面 | 正常打开，能进入项目管理、模型管理；空库列表为空属于正常状态 |
| 日志和备份 | 无启动异常，`backups/` 有本次生成的备份；备份存在不等于恢复已验证 |

全部满足后记录「正式离线包在本机 WSL + Docker Desktop 中，通过 scripts/deploy.sh 完成首次部署与页面启动验证」。没有执行的模型、仓库、升级和恢复测试不记为通过。

### 7.6 结束验证与失败处理

在本次部署目录停止测试服务，保留配置和数据，便于复查：

```bash
docker compose -p codereview stop app
docker compose -p codereview stop mysql
```

如需移除本次容器和网络，在确认它们确实属于本次验证目录后，按运维手册执行 `docker compose -p codereview down`。数据库绑定目录仍保留；不删除部署目录或运行全局 Docker 清理。

| 失败位置 | 处理 |
| --- | --- |
| Docker 不可用 | 核对 Desktop 已启动、Ubuntu 的 WSL 集成及本机上下文 |
| Windows 挂载目录被拦截 | 在 WSL Linux 目录重新解压原包，不关闭文件系统检查 |
| 内存或实际磁盘不足 | 处理 WSL／Docker 可用资源，再从原验证目录重测 |
| Docker 数据目录在 Ubuntu 中不可见 | 保存预检输出，修复脚本的跨环境探测后重测，不将其当作应用启动已通过 |
| `.env` 密码为空 | 核对是否提前创建了空 `.env`；不要在已有数据库上重新随机生成密码 |
| 数据库、账号、备份或应用初始化失败 | 保留完整日志及现场，定位并修复正式包；不要改用单独 Compose 启动代替脚本结果 |
| 容器正常但页面不可达 | 核对本机端口映射、Windows 访问地址和 Docker Desktop 网络；仅容器健康不能代表页面验证通过 |
